# Build details

Read on demand from CLAUDE.md, which has the everyday commands. Linux, profiling, ASan, versioning, packaging and the test app.

- **Linux** (GCC ≥ 13, x86-64): `./Generate-Linux.sh` (= `vendor/premake/bin/premake5 gmake`, 5.0.0-beta8; unlike the `.bat` it doesn't pause), then `make -j"$(nproc)" config=<debug|debug-asan|release|distribution> [Project]`; outputs land in `build/bin/<Config>-linux-x86_64/`, the vendor projects' makefiles in `build/make/` (inside their submodules they would overwrite FreeType's tracked `Makefile`). `VULKAN_SDK` must be LunarG's tarball (Ubuntu's Vulkan headers and shaderc are too old), and assimp 6.0.4 is built from source into the git-ignored `vendor/assimp/lib/linux-x86_64/` (LINUX-SUPPORT.md Appendix A). The Vulkan loader is never linked (`vk::DynamicLoader`), D3D sources are left out, and `DE_DEBUG_BREAK` raises `SIGTRAP`. Headless check: `xvfb-run scripts/ci/linux-smoke-test.sh <Config>` (needs `mesa-vulkan-drivers` and `python3-xlib`; with `gdb` a run still alive 60 s after its close leaves its threads in the output, as cdb does in `scripts/ci/windows-smoke-test.ps1`). For a tester on a real desktop, `scripts/linux-tester/make-bundle.sh <Config> <out.tar.gz>` packs the test app and examples with `run-checks.sh` (the same runs on the tester's desktop, closing only its own windows, into a report archive), `play.sh` and a checklist README; CI's Distribution job uploads it as the `DingoEngine-linux-tester` artifact. LINUX-SUPPORT.md tracks what is done and what's left.
- **Third-party notices** (v1.0 P10): `THIRD-PARTY-NOTICES.md` at the root lists every third-party component a game ships with and its licence text, generated by `scripts/gather-notices.sh` from `scripts/notices/components.txt` (a licence file, or `file@marker` for one embedded in a source header; the SDK and assimp pieces that aren't submodules keep their texts in `scripts/notices/licenses/`). Every release archive, packaged example, the test framework and the tester bundle carry it; `build-linux.yml`'s Debug job runs `--check`, so a vendor bump or a new dependency that forgot to regenerate fails. Add a component to the manifest when it starts being linked. The examples and the test app draw their text in Inter (OFL-1.1, `assets/fonts/Inter-Bold.ttf`, the test app also `Inter-Regular.ttf`; Arial until P10), with `LICENSE-Inter.txt` at each assets root, which packaging copies beside the executable.
- **API reference** (v1.0 P11, D7): `mkdir -p build/docs && doxygen docs/Doxyfile` (Doxygen 1.9.8, `apt install doxygen`) writes `build/docs/html` from `include/DingoEngine` plus `docs/*.md` (`docs/README.md` is the main page; headings get GitHub-style ids, so in-page `#anchor` links work in both) and every warning to `build/docs/warnings.txt`. `Dingo::Internal` is excluded. `.github/workflows/docs.yml` fails a PR that touches `include/` or `docs/` with any warning (an undocumented public declaration, an unresolved guide link) and deploys the HTML to GitHub Pages from master (Settings > Pages > Source must be "GitHub Actions"). Doxygen doesn't warn about undocumented enums, so they're on the reviewer. A guide can't link to `README.md` (the main page): Doxygen can't resolve it.
- **New executable checklist**: any project linking the engine must call `copyAssimpRuntime()` (shared helper in the root `premake5.lua`) from its own `premake5.lua`, or it dies with `STATUS_DLL_NOT_FOUND` (`0xC0000135`) before `main` — in Debug-ASan it also copies the ASan runtime DLL. On Linux the same call gives the executable the engine's whole link list in a link group, since `make` links only the libraries a project names. A game that ships packed assets also calls `embedPackKey()` (after `copyAssimpRuntime()`; it reads the project's `dpak.key`, made by `DingoPack genkey`, when premake runs) and passes `Dingo::Generated::GetPackageKey()` (`<DingoPackKey.h>`) as `ApplicationParams.Assets.PackageKey`. Also add it to `.github/workflows/build-release.yml`'s Windows packaging (one job per example, zipping the Distribution job's `<Example>/` folder: exe, DLLs and the `<Example>.dpak` its "Pack example assets" step writes for every `examples/*` with `scripts/pack-assets.ps1`; on Linux `scripts/package-linux-programs.sh` packs every `examples/*` with `scripts/pack-assets.sh`, and the test framework with its loose assets, for the release and for `build-linux.yml`'s Distribution artifacts) and the `.vscode` build/launch entries. Call `distributionSymbols()` before `copyAssimpRuntime()`, or its Distribution PDB is left out of the release's symbols zip. Give an example `exeMetadata { Name, Description, Company, Copyright }` after `copyAssimpRuntime()` (`Version` defaults to the engine's) and an `icon.ico`/`icon.png` beside its `premake5.lua` (`scripts/icons/make-icons.sh` draws the placeholder tiles from `icons.txt`): a generated `.rc` (version resource, the icon as `GLFW_ICON`; each is left out when its field or file is missing) on Windows, and the `.desktop` template plus `<Project>.png` in `build/generated/<Project>/`, with `install-desktop-entry.sh`, that `scripts/package-linux-programs.sh` ships on Linux (docs/distribution.md "Name, icon and version"). On Linux the engine's post-build step also merges the engine, every vendor lib and the static assimp into `build/dist/<cfg>/libDingoEngine.a` (`scripts/merge-static-libs.sh`), the twin of Windows' `lib.exe` merge.
- **Profiling** (v0.9 P1): `premake5 --profile vs2026` compiles Tracy v0.11.1 (`vendor/tracy`, upstream `wolfpld/tracy`, not a fork yet) into the engine with `TRACY_ON_DEMAND`; `DE_PROFILE` is workspace-wide so games' `DE_PROFILE_*` zones (`Core/Profiler.h`, Tracy-free) compile in too. Without the option the macros are empty and no Tracy code links. CI's master build adds one Release `--profile` job. GPU pass timers (`Renderer::BeginGpuTimer/EndGpuTimer`, `Internal::GpuTimers`) are always on: NVRHI timer queries in a 4-frame ring, read in `BeginFrame` while the render thread is parked (D3D11 reads them through the immediate context), at most 32 a frame. See docs/profiling.md.
- **CI** (v1.0 P7): both workflows run on every push to master and by hand (`workflow_dispatch`; pull requests run neither). The Linux workflow (`build-linux.yml`) builds Debug, Debug-ASan, Release and Distribution with GCC and runs `scripts/ci/linux-smoke-test.sh` in each under Xvfb and llvmpipe: the unit tests, every test case, every example, Marionette's `--check`, the test app's `--graphics=headless` check with `DISPLAY` unset (#249), then the test app's `--crash=` runs, whose report must be in the log; Release adds `--tournament=10 --seed=1 --player-tier=3` (`SMOKE_TOURNAMENT=1`, about 5 minutes), Debug-ASan turns leak detection on past `scripts/ci/lsan.supp` (libxcb and Mesa only). The Windows workflow (`build-windows.yml`) builds Debug, Release, Distribution and a `--profile` Release, and in Release runs `scripts/ci/windows-smoke-test.ps1`, the PowerShell twin, on WARP (DX11 and DX12; no Vulkan driver there) with the tournament, the headless check and the crash runs, which must leave a minidump. Both judge by exit codes, `[FAIL]`, sanitizer reports and `LOG ERROR`, never by timings.
- **Unit tests** (v1.0 P7, doctest v2.4.11, `vendor/doctest`, a submodule of upstream): `test/UnitTests` builds `Dingo-UnitTests`, a headless console app over pure engine code (`Frustum`/`AABB`, `LightMath`, `Utf8`, `UUID`, the `.events` line parser `Internal::ParseEventsLine` in `Graphics/EventsFile.h`, `Internal::ShadowAtlasAllocator` in `Graphics/ShadowAtlasAllocator.h`, and `ToneMapping.glsl` itself compiled as C++ over GLM through a small shim; v1.0 P8: `SaveData`, its files and slots, `Settings`' format and `ChooseDisplayMode`, plus a writer the test kills mid-write: `Main.cpp` runs `--save-writer=<path>` before doctest, and the test spawns its own executable with it); run it from anywhere, with doctest's flags (`-tc=`, `-ts=`). It reaches engine internals through `src/` on its include path. New pure code gets its tests there; anything needing a window or device stays in the test app's checks.
- **Debug-ASan** links and runs (v0.6.3); Linux CI runs it (above). The Vulkan SDK's shaderc/SPIRV prebuilts are non-ASan, so the configuration defines `_DISABLE_STRING_ANNOTATION` / `_DISABLE_VECTOR_ANNOTATION` workspace-wide; dropping them brings back ~500 `LNK2038 annotate_*` mismatches. The MSVC linker needs no `-fsanitize` flag (cl embeds `/INFERASANLIBS`); GCC does, so Linux adds it.
- **CI setup**: every Windows job sets up through `.github/actions/setup-windows` (Vulkan SDK with its debug libraries, cached under the same key everywhere; premake on `PATH`; MSBuild on `PATH` with `msbuild: true`), the twin of `.github/actions/setup-linux`. Change the SDK, the premake version or the setup steps there, not in the workflows.
- **PR lint** (`lint.yml`, on pull requests that touch C/C++ or premake files): `premake5 --lint` generates projects that compile syntax-only (`-fsyntax-only`, `/Zs`) with extra warnings (`-Wall -Wextra`, `/W4`) and no PCH, and `scripts/ci/lint-changed.sh [base]` compiles only the files changed since `base` plus every file that includes a changed header, transitively, matched by file name. Linux goes through make's per-object targets, Windows through MSBuild's `SelectedFiles`, passed in a response file because no command-line quoting gets a `;` list through. Warnings become annotations and a step-summary table (vendor/ and build/ dropped); only a compile error fails the job. To run it locally: generate with `--lint`, run `scripts/ci/lint-changed.sh origin/master` from Git Bash or Linux, and re-run premake without `--lint` before building normally.
- **Version** (v1.0 P9, A106): `VERSION` holds `major.minor.patch`; premake writes the git-ignored `include/DingoEngine/BuildInfo.h` (`DE_ENGINE_VERSION_*`, read by `Application::GetEngineVersion/GetEngineBuildNumber`) from it on every generate, `DE_VERSION` (a release tag, `v` optional) overriding the file and `DE_BUILD_NUMBER` (CI's commit count) the build number, 0 by default. `VERSION` trails the release branch, so the branch/tag is the reliable "what am I on". SemVer from 1.0.0: docs/versioning.md.
- **PCH**: `depch.h` / `depch.cpp`.

## Test app and devices

The test framework takes `--test=<name substring>` (case-insensitive) to boot straight into one case — `--test=asset`, `--test="text test"` (plain `text` would match "Texture Quad Test" first) — otherwise it starts on the first. `--crash=segv|thread|engine-thread|engine-throw|engine-stack|prepared-throw|prepared-stack|abort|terminate|throw|stack|verify|fatal` crashes on purpose at its 30th update (v1.0 P7).

Device and adapter selection lives in `Graphics/NVRHI/` (`VulkanGraphicsContext.cpp` for Vulkan). Without a hardware GPU (a VM), D3D11 takes the default adapter, which is WARP, and D3D12 falls back to WARP with a warning (v0.8.2); Vulkan without a driver stops at instance creation with a `DE_CORE_VERIFY` and logs the missing extensions or layers. WARP rasterizes on the CPU: fine for running the test app, meaningless for timings. The Vulkan validation layer loads in Debug and Debug-ASan only, unless `GraphicsParams::VulkanValidation` or `--vulkan-validation[=off]` says otherwise (v1.0 P7: in Release it cost ~0.6 ms of render CPU a frame). `GraphicsContext::SupportsWireframe()` is false on a Vulkan GPU without `fillModeNonSolid`; `NvrhiPipeline` then builds `FillMode::Wireframe` solid and warns once (v0.8.3, #78).
