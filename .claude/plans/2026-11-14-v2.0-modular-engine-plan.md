# 2.0 — Modular engine

## Goal (owner, 2026-11-14)

The engine provides interfaces so a game can build its own engine modules, for example a scene that
takes its own 2D or 3D physics, and the renderer taking interfaces at init. The engine implements
and ships a default for each, so a game never has to write its own renderer, physics or audio. The
roadmap entry is [ROADMAP-1.x.md](../../ROADMAP-1.x.md#modular-engine-the-20-theme-r5) (R5), next to
the engine layers (R4).

This is a design note for a major release, not a phase plan. Each phase below gets its own plan with
`file:line` anchors when it starts.

## Review

The first proposal made every built-in scene system replaceable (`ReplaceSystem<T>`), gave systems
an `OnRender`, and required a null twin for every interface. A `fable-advisor` review on 2026-11-14
found that it freezes far more than the goal needs. The shape below is the review's. Its code claims
were checked against master `be8a5d2`:

- **Built-in systems depend on each other.**
  - Ragdolls live inside physics (`src/DingoEngine/Scene/Systems/PhysicsSync.h:204`).
  - Interpolation reads physics (`Systems/PhysicsInterpolation.h:31`).
  - Animation takes scripts, physics and the renderers' visibility (`Scene.cpp:396-399`).
  - Every reader shares the transform and mesh memos (`SceneData.h:76-95`).

  A replacement physics system would have to rebuild all of that.
- **The tick is an interleaved loop, not a list of systems.** Scripts, deferred destroys,
  interpolation, the physics step, constraint breaks and the tick count alternate inside one fixed
  tick (`Scene.cpp:356-375`), and a second, per-frame physics path sits at `Scene.cpp:404-409`.
- **`Scene` is the physics and audio API games call**: `CreateRigidBody`, `ApplyImpulse`,
  `GetSensorOverlaps`, `PlayAudioSource` (`Scene.cpp:1033-1177`). A replacement would have to answer
  all of it.
- **The backend interfaces are large**: `Physics3D` has 54 pure virtuals, `Physics2D` 20 and
  `AudioEngine` 58. A game implementing one freezes it.
- **Audio is process-wide**: `AudioSync` calls `Application::Get().GetAudioEngine()`
  (`AudioSync.cpp:46`, `:104`, `:139`), with one listener.
- **Systems can't reach entities**: EnTT is private (`SceneData.h:3-5`), and the only public
  iteration is `Scene::ForEachEntity(std::function)` (`Scene.h:239`), one entity at a time with no
  component filter.

## Shape: three extension points

| Point | A game may | Frozen for 2.x |
|---|---|---|
| Physics backends (`Physics2D`, `Physics3D`) | replace them through an application-level factory | the interfaces, every virtual with a default body |
| Scene systems | add its own at named phases; turn built-ins off | four phases and one small base class |
| Scene renderer | replace it whole; hook a few named points | `Render(scene, view)` and the hook points |

### Scene systems

```cpp
struct SceneTick { std::uint64_t Index; float Step; bool Resimulating; };
struct SceneSystemInfo { std::int32_t Order = 0; bool RunWhenStopped = false; };

class SceneSystem
{
public:
	virtual ~SceneSystem() = default;
	virtual void OnAttach(Scene&) {}
	virtual void OnStart(Scene&) {}
	virtual void OnStop(Scene&) {}
	virtual void OnPreTick(Scene&, const SceneTick&) {}
	virtual void OnPostTick(Scene&, const SceneTick&) {}
	virtual void OnUpdate(Scene&, float deltaTime) {}
	virtual void OnLateUpdate(Scene&, float deltaTime) {}
	virtual void OnEntityDestroyed(Scene&, Entity) {}
};

SceneSystemRegistry::Register<WeatherSystem>("Game.Weather", { .Order = 10 });
Scene scene({ .Features = SceneFeatures::All & ~SceneFeatures::Physics3D });
```

- **Phases.**
  - `OnPreTick`: before the scripts' `OnFixedUpdate`.
  - `OnPostTick`: after the physics step and the write-back.
  - `OnUpdate`: after the scripts' `OnUpdate`.
  - `OnLateUpdate`: transforms are final.

  Order within a phase is `Order`, then registration order. Only the phase boundaries are public
  behaviour. The built-ins' internal order is not, so it can still change in 2.x. There is no
  dependency graph.
- **No `OnRender`.** Rendering reads the scene (see below).
- **No `ReplaceSystem<T>`.** `SceneParams::Features` turns physics 2D/3D, audio, animation or
  particles off, and a game adds its own system in their place. The `Scene` calls that belong to a
  disabled feature already do nothing without a world.
- **Built-ins stay concrete** behind the phases, so the shared memos stay.
- **Per-entity state** follows the engine's own pattern: runtime components (`RuntimeComponents.h`),
  built lazily in the system's pass and dropped on remove. 1.3's `ComponentRegistry` gains a
  `Runtime` option: not saved, not duplicated, cleared at `OnStop`.
- **Removal callbacks only** (`scene.OnComponentRemoved<T>(fn)`), as the engine uses today
  (`PhysicsSync.cpp:690-694`, `AudioSync.cpp:130`). New components are found by polling "has T,
  lacks the runtime", so no construct callback can re-enter the registry.
- **Threading**: every callback runs on the main thread. Only the constructor and `OnAttach` may run
  on a loading thread, with no GPU work and no `Application`. The scene sets `Updating` around each
  call, so `DestroyEntity` defers. No parallel systems in 2.0.
- **Prerequisite**: a public `Scene::Each<T...>(fn)` query that filters by component.

### Application level and per scene

- **Application level**:
  - the window, graphics context, renderers, scene renderer, audio engine and asset manager;
  - loader registration;
  - the component, script and system registries;
  - the physics backend factories (Jolt's start-up state is process-wide).
- **Per scene**: physics world instances, system instances and runtime components.
- **No `IModule` type.** A module is a `RegisterX(Application&)` function that registers types,
  loaders and panels. It may push a `Layer` for anything with a lifetime, since `Layer` already
  carries the teardown guarantee.
- **Audio has one listener for the process.** A scene gets an "audible" flag, so an editor's edit
  scene and play scene don't fight over it.

### Backends

- Every `Physics2D`/`Physics3D` virtual gets a default body that does nothing, so the base class is
  the null physics and new virtuals can be added in 2.x. A conformance test in `test/UnitTests` runs
  against Box2D and Jolt and against any game's backend.
- **Audio stays engine-implemented**, with a null device chosen through `ApplicationParams` for
  servers and CI. Whether miniaudio's null backend is already wired is not checked yet.
  `GraphicsContext` and windowing stay concrete.
- **A headless server uses real Jolt with no GPU**, which headless mode already allows. Null physics
  is for tests, and headless mode already serves as the null renderer.

### Scene renderer

- `Renderer3D.h` is 72 KB, and no interface over it would be useful. The replaceable thing is
  `SceneRenderer`, whose surface is `Render(Scene&, Framebuffer*, bool)` (`SceneRenderer.h:39`).
- The render-side state leaves the scene and moves to the scene renderer, keyed by scene and view:
  the 2D sort buffer, mesh memo, shadow probes, static bakes and skinned views (`SceneData.h:62-105`).
- The skinned-visibility feedback from the renderer into animation (`Scene.cpp:396-399`) needs a
  design of its own.
- New `Render(scene, RenderView{ View, Projection, Target })`. The editor camera and picking need it,
  and it can ship in 1.5.
- **Pass hooks come last.** PBR (1.4), renderer scale (1.7) and the 2.0 UBO redesign all change the
  passes, and hook points make them public. Ship three or four semantic points, each saying which
  thread it runs on.

## What it means elsewhere

- **Networking**: the tick becomes a callable unit (an internal `RunTick` taken out of
  `Scene.cpp:356-375`; `SetTick` exists at `Scene.cpp:482`). `OnPreTick` applies inputs,
  `OnPostTick` captures state, and replication reads 1.3's reflection.
- **Editor**: `RunWhenStopped` covers preview systems. Play and stop work only if every system can
  rebuild its state from components at `OnStart`. That's the contract.
- **Fixed tick**: delete the per-frame physics path before the phases go public, or each phase means
  two things.
- **Scene files**: systems are registered by name at application level and created for every scene.
  A scene file doesn't list systems in 2.0.
- **GPU teardown**: systems die with their scene in `Layer::OnDetach`, before
  `RendererBackend::Destroy` (`Application.cpp:298-306`). Registries hold factories, never GPU
  objects. A debug assert after the layers detach checks that no scene is still alive.

## Decisions (proposed, waiting for the owner)

- **M1. Three extension points**, as above: no replaceable built-in systems, no `OnRender`, and no
  rule that every interface needs a null twin.
- **M2. 1.x carve-out**: `docs/versioning.md` says that implementing `Physics2D`/`Physics3D`
  outside the engine isn't covered by the 1.x promise, so 1.6's 2D queries can still add virtuals.
  *Alternative: give every virtual a default body in 1.6. That's additive, but it decides the null
  behaviour of 74 functions early.*
- **M3. v1.6 injects a factory, not a world pointer.** A scene creates its worlds on start and
  destroys them on stop (`PhysicsSync.cpp:71`, `:86`, `:112`, `:127`), so a pointer can't survive a
  restart, and its ownership would be unclear.
- **M4. Audio stays concrete**, with a null device. *Alternative: a public audio backend. 58
  functions to freeze for little gain, since miniaudio covers every platform.*
- **M5. How 2.0 lands.** Five breaks share one major: layers, systems, `unique_ptr`, PBR by default
  and the fixed tick by default. CI smoke-tests only master, so a long-lived 2.0 branch would go
  untested. *Proposed: after the last 1.x minor, master becomes 2.0 development, with each phase
  merged on its own and 1.x fixes on a `v1.x` maintenance branch. Alternative: a long `v2` branch
  with CI turned on for it.*

## Safe to start in 1.x (nothing new frozen)

- The internal `RunTick` extraction and one internal shape for the built-in systems.
- A public `Scene::Each<T...>` query.
- 1.3's registries, with the `Runtime` component option.
- The 1.6 physics factory, with M2's carve-out.
- `Render(scene, RenderView)` in 1.5.
- The layer include lint, reporting only.

## Phases for 2.0 (each mergeable on its own)

1. **Mechanical breaks**:
   - remove the deprecated APIs;
   - make the fixed tick the default and delete the per-frame physics path;
   - factories return `std::unique_ptr` (smart pointers plan, phase 3).
2. **Engine layers, bottom-up** (ROADMAP-1.x.md, "Engine layers (2.0)"):
   - `Application` and `Settings` move up;
   - loaders are registered from above;
   - Physics→Graphics and UI→Scene are broken;
   - the lint is enforced.

   The teardown rewrite lands here and needs GPU runs on all three backends.
3. **The scene holds data**: the render state moves into `SceneRenderer`, `RenderView` arrives, and
   the scene renderer becomes replaceable.
4. **Backends**: default bodies, the application-level factories, null physics, the conformance
   test and the audio null device.
5. **Public `SceneSystem`**, its registry and `SceneParams::Features`. The networking module moving
   onto it is the proof.
6. **Render hooks**, after the UBO and material redesign and PBR by default.
7. **Migration guide and showcases**: a dedicated-server example with `--check`, and an example with
   a system the game wrote.

## Left out

- Replacing built-in systems, system dependency declarations, parallel systems.
- A public `IRenderer` or audio backend; games implementing `GraphicsContext`.
- Linker-enforced layer libraries (the lint is enough for 2.0).
- System lists in scene files.
- Not checked yet: how 1.3 stores a game's component types in the hidden EnTT registry, which the
  `Each` query and the removal callbacks depend on. Its P3 settles it.
