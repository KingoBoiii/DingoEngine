## 1. Where we start (verified facts)

### 1.1 What a static mesh costs today

| Area | Today | Anchor |
|---|---|---|

### 1.3 Materials and skinning

- **Lit surface values are per material.** `EmissiveColor`, `EmissiveStrength`, `Roughness` and
  `Specular` live in `MaterialParams`, and the header tells games to "give an entity its own lit
  material" (`Material.h:34-46`). Each material is its own batch key, so a per-entity glow costs a
  material, a VB/IB pair and two draws. `PrepareLitMaterial` uploads `LitMaterialData` once per
  material per `EndScene` (`Renderer3D.cpp:842-868`).
- **Skinned**: one draw per submission after the static batches. A palette is a volatile `SkinData`
  write per instance (`MaxSkinnedInstances` 64, at most 256; the UBO allows 2× for the shadow
  re-upload). There is no skinned culling and no animation LOD (`Renderer3D.cpp:598-832`,
  `Renderer3D.h:77,280-302`).

### 1.4 What we have measured

- v0.8 plan: a flat 10k-mesh scene is **4.35 ms a frame** in Release, about 3 ms of it
  `RenderEntities3D`'s vertex transform (`2026-10-01-v0.8-animation-plan.md:189,397`).
- *Candlewick* (v0.7): 1.8–2.1 ms a room in Release at 1600 × 900, but **13–14 ms in Debug**,
  "spent CPU-transforming all ~330 meshes every frame" (`2026-10-01-candlewick-plan.md:560-562`).
- v0.9 GPU verification on the RX 7900 XTX (`2026-10-06-v0.9-shadows-post-vfx-plan.md:795-819`):
  the new passes cost 0.07–0.11 ms each. *Marionette*'s P0 frame is 1.92–2.20 ms on Vulkan against
  0.49–0.95 ms on D3D, with Vulkan's render CPU at 0.79–0.88 ms against 0.14–0.15 ms. **The
  renderer's CPU side is the budget, not the GPU**, and Vulkan's submission path is the worst of it.
- No per-room `--perf` results were recorded for *Candlewick* or *Marionette* on v0.9.

### 1.7 Stability, platform, docs and shipping

- **Logs and crashes**: spdlog writes `Dingo.log` relative to the **cwd**, truncated every run
  (`Log.cpp:51`). There is no crash handler (no SEH filter, `sigaction` or minidump). `DE_VERIFY` stays
  on in Distribution and ends in `DE_DEBUG_BREAK`, which without a debugger is a crash with no
  message (`Assertion.h:7-20`).
- **Tests**: there is no unit-test project. The windowed test app has 19 cases; 8 log `[PASS]`/`[FAIL]`
  through `TestChecks.h`, and five commented-out cases remain (`TestLayer.cpp:51-75`). **Windows CI
  only builds** (`build-master.yml`). Linux CI runs every case, every example and *Marionette*'s
  `--check` under Xvfb and llvmpipe (`scripts/ci/linux-smoke-test.sh`). Neither CI runs Debug-ASan,
  leak checks, `--tournament` or a soak.
- **Platform**: Linux is done except L26 (real GPUs and desktops, which needs hardware) and L27
  (native Wayland, "a decision before it is work"). The Linux release job has **never run on a real
  tag** (`LINUX-SUPPORT.md:191`). macOS is not mentioned anywhere.
- **Colour**: every swap chain and colour texture is UNORM (`VulkanSwapChain.cpp:37-42`,
  `DirectX11SwapChain.cpp:133`, `DirectX12SwapChain.cpp:137`, `NvrhiTexture.cpp:23-26`). There is no
  sRGB `TextureFormat`.
- **Docs**: 15 hand-written guides, 4,614 lines. There is no API reference and no Doxygen.
  `CLAUDE.md:166` lists 9 of the 15. The `LINUX-SUPPORT.md` header (:13-14) is stale. README's
  dependency table leaves out assimp, miniaudio and tracy. There are 102 public headers, 39 of them
  in Graphics.
- **Shipping a game**: there is no serialization or save data (no JSON/YAML library;
  `Platform::GetUserDataDir` is used only by the shader cache). `Dingo::UI` is an ImGui facade for
  debug panels (#98). There are no audio buses (#95), and VSync can only be set at window creation
  (#87). Fullscreen does toggle at runtime (`Window.h:83-85`).
- **Licensing**: the engine is MIT. There is **no third-party notices file**, and neither release
  packaging step ships a vendor licence. Eleven example asset folders ship Arial Bold (`arialbd.ttf`),
  which is not redistributable, and the test app also ships Arial Black.
- **The game**: ROADMAP names *Dungeon Crawler* (1.0) as the release game (`ROADMAP.md:403`), and
  its v0.5 section moved it into **its own project, built on prebuilt engine releases**
  (`ROADMAP.md:78`). D1 replaces it with a new in-repo game (§6). The in-repo `DungeonCrawler` (2D, 1,084 lines) and
  `DungeonCrawler3D` (1,682 lines) are prototypes: one level, no audio, no menus, no progression, no
  saves, and parented OBJ-part rigs rather than skeletal characters.

## 2. Design

v1.0 is the release where the engine promises to stay put. Everything below serves one of three
goals:

1. **Throughput**: the frame cost follows what is visible, not what exists.
2. **Stability**: a shipped game that fails tells its player and its developer why, and every
   backend is checked by CI rather than by hand.
3. **A stable, documented API**: what `include/DingoEngine` exposes after v1.0.0 changes only by
   SemVer.
4. **Games get a UI of their own**: DingoUI (§2.8) draws HUDs and menus, so no game builds them
   from sprites and text by hand again (#98).

The rendering rule of every earlier milestone stays, with one stated exception (D2): **a scene that
doesn't opt in renders exactly as before (0 px)**. Culling, retained submission and static bakes are
CPU-side reorderings of the same float operations, so they must hold 0 px. Instancing moves the
transform to the GPU, so it gets a tolerance gate instead.

### 2.1 Measuring first: the Throughput Test and perf baselines

A new test case, `--test=throughput`, gives the plan its yardstick. Its modes:

| Mode | Scene |
|---|---|
| `static` | N unique static meshes in a grid |
| `repeat` | N copies of a few props: crates, pillars, torches |
| `mixed` | a dungeon-sized layout of both, with a camera flying through so most of it is off-screen |
| `skinned` | N Foxes |
| `shadow` | `mixed` under a casting sun and 8 casting point lights |

It takes `--count=N` and `--perf` (mean CPU ms of `RenderEntities3D`, `EndScene` and the frame, plus
GPU timers over 600 frames). It logs `[PERF]` lines that scripts read, as *Marionette*'s `--perf`
does.

P0 also records `--perf` for *Candlewick* (each room) and *Marionette* (`--bout=1 --autoplay`) on
all three backends, in Release and **Debug**. Debug is what a developer iterates in, and *Candlewick*'s
13–14 ms there is the most visible symptom.

**Targets** (RX 7900 XTX, Release, VSync off; targets, not promises):

| Scene | Today (P0 measures) | Target |
|---|---|---|
| `mixed`, 10k meshes, ~10% visible | 5.79 ms CPU (5.05 + 0.74), 6.2 ms frame, 8 draws, 9.4% visible | `RenderEntities3D` + `EndScene` ≤ 0.5 ms CPU |
| `repeat`, 10k instances of 5 meshes | 7.56 ms CPU (6.53 + 1.03), 8.0 ms frame, 13 draws | ≤ 0.3 ms CPU, ≤ 15 draws |
| *Candlewick* Debug, worst room | 16.2 ms frame, 14.4 ms render CPU (Vulkan, room 3; DX11 14.6, DX12 15.3) | ≤ 6 ms |
| A frame with nothing new opted in | P0's tables (§9) | equal to P0 within noise |

"Today" is P0's Release Vulkan without layers, the mean of three runs (§9 "P0 Part B"); DX12 is
within 0.1 ms of it on both throughput rows.

### 2.2 Retained submission and culling

**`SubmitMesh` stops transforming.** It records `{ Mesh*, transform, colour, BatchKey, object
data }` into a per-scene list. `EndScene` runs in this order:

1. Resolve lights. This is the first point at which every light and every mesh is known, whatever
   order the game submitted them in.
2. Cull against the camera frustum. The test is the mesh's model-space AABB transformed to a world
   AABB (Arvo's method), against `ExtractFrustumPlanes`.
3. Cull casters per shadow view. A caster is kept for a cascade or tile when its AABB touches that
   view's volume. The cascades' depth range is fitted to the surviving casters' AABB, as today.
4. Transform the survivors into chunks, with the same per-vertex arithmetic in the same order. That
   keeps 0 px: only geometry that cannot reach a pixel is removed.

A mesh that is culled for the camera but kept for a shadow view goes only into the shadow chunks,
like `ShadowsOnly`.

- **Public maths**: `Graphics/Frustum.h` gets `Frustum::FromViewProjection`, `Intersects(AABB)`,
  `Intersects(sphere)` and `AABB::Transformed(mat4)`. It replaces the file-local helpers and lets
  *Candlewick* delete its copy.
- **Distance culling**: `MeshRendererComponent::CullDistance` and
  `SkinnedMeshRendererComponent::CullDistance` (0 = never, the default). Each is checked against the
  camera position, with no fade.
- **2D**: `RenderEntities` skips sprites, circles and text whose world rectangle misses the
  orthographic view. This is cheap, and 2D games get it for free.
- **Skinned**: culled by the rest-pose bounds padded by half, the rule the caster AABB already uses.
- **Stats**: `CulledMeshes`, `CulledCasters` and `CulledSkinned`, shown in F4. A debug toggle,
  "freeze culling frustum", lets you fly out and look at what was kept.

The retained list is also what makes everything after it possible: instancing, static bakes and
per-object data all need to see the scene's submissions as a whole.

### 2.3 One upload arena instead of a buffer pair per batch

Today each `BatchKey` owns full-capacity VB/IB pairs, 3 MiB of vertices each, so every new material
costs memory and allocations as well as draws. Instead:

- Each `Renderer3D` gets **one per-frame vertex arena and one index arena**: a ring of 4 frames, each
  frame's slice grown to the high-water mark.
- Each chunk becomes an offset and a count in the arena, drawn with a `baseVertex` and `startIndex`.
- `MaxVertices` and `MaxIndices` stop meaning "per batch" and only bound one draw. The index
  format follows the buffer (16- or 32-bit, `NvrhiCommandList.cpp:222-223`), so the arena's indices
  are 32-bit and a chunk is bounded only by one draw's size.
- A second scene in the frame appends after the first instead of overwriting the pool. That removes
  the "rewrite a buffer that is still bound" pattern for these buffers, the pattern behind #145. #145
  itself was fixed at its source on master (#148: `NvrhiGraphicsBuffer::Write` puts a written buffer
  back into its initial state), since `Renderer::Upload` is public.

This is the buffer half of "material sharing": a custom material costs one more draw, not one more
pair of 3 MiB buffers.

### 2.4 Per-object data (the other half of material sharing)

There is one **object buffer** per scene, a storage buffer of 64 B records:

```
struct ObjectData { vec4 Color; vec4 Emissive; /* rgb, strength */ vec4 Surface; /* roughness, specular, flags, _ */ uvec4 _pad; }
```

- **Built-in shaders only.** The default and lit materials get an engine vertex with a `uint
  a_ObjectIndex` (52 B). Their shaders read the colour and the surface values from the record
  (binding found by name, like `SkinData`). Custom materials keep today's frozen 48 B layout and
  their own bindings, untouched.
- **Component**: `MeshRendererComponent` gains an optional `SurfaceOverride { Emissive, EmissiveStrength,
  Roughness, Specular }`, an `std::optional` set through a fluent `SetSurface`. When it is set, the
  record's values replace the material's. The direct API gets the same thing through
  `SubmitMesh(..., const SurfaceOverride*)`.
- **What it buys**: *Candlewick*'s glowing props, EchoVault's orbs and DungeonCrawler3D's treasure
  stop needing a lit material each, so a whole level draws in one batch per shadow mode again.
- **0 px**: a default record reproduces today's values exactly. The colour moves out of the vertex
  into the record but reaches the fragment stage unchanged, and the lit maths is untouched. The
  broken-build control checks this.

### 2.5 GPU instancing (D3)

The same `Mesh` drawn with the same `BatchKey` many times in one scene is **one draw**:

- **Buffers**: a `Mesh`-owned immutable VB/IB, made on first use and freed in `~Mesh` and on
  `Reinitialize`, exactly the skinned path's lifecycle. Skinned meshes already have one; static
  meshes get the same.
- **Instance data**: the object buffer from §2.4 grows an instanced record with the model matrix
  (3 × `vec4`) and the normal matrix (3 × `vec4`), which the CPU computes once per instance.
  `gl_InstanceIndex` plus a base offset in a small per-draw uniform picks the record (v0.9's D5:
  storage buffers, not instance attributes). There are no new pipeline features and nothing
  new for D3D11.
- **Shaders**: the built-in shaders get a `DE_INSTANCED` variant, made on the first instanced draw,
  as `DE_SKINNED` is. Custom materials are instanced only if they say so, through
  `MaterialParams::SetInstancing(true)` plus a shader that declares the instanced block. Otherwise
  they stay on the CPU batch path, which still works for every shader.
- **When to instance**: a mesh with at least `Renderer3DCapabilities::InstanceThreshold` copies in
  the scene (default 8), or a smaller count whose vertex total exceeds a chunk's worth. Below that,
  the CPU batch is cheaper: one draw for many small unique meshes.
- **Shadows**: instance × view runs as one draw with `instanceCount = instances × views`, and the
  view index is `gl_InstanceIndex % views`, the same trick the shadow pass already uses per view.
- **Pixels**: GPU and CPU transforms round differently, so the result is not 0 px (D2). The gate is
  "no pixel off by more than 2/255, at most 0.1% of pixels off at all, and no geometry missing or
  added," checked against a forced-CPU run (`Renderer3DCapabilities::Instancing = false`, which also
  stays as the escape hatch).

### 2.6 Static geometry (D4)

For geometry that never moves, even the per-frame retained list and culling loop are waste:

- **Component**: `MeshRendererComponent::Static` (default `false`).
- **Bake**: the scene bakes static entities **once** into persistent, world-space buffers. The bake
  is the CPU transform today's batch already runs, so it is 0 px. The baked geometry is split into
  spatial **cells** of at most 64k vertices, each with an AABB, so culling still works per cell.
- **Draws**: a cell draws per `BatchKey` from its own immutable buffers, with no upload per frame.
  Shadow views cull cells the same way.
- **Change detection**: every frame, a static entity's **draw state** is compared with the one it
  was baked at: world transform, `Mesh::GetId()` (which catches a hot-reload), colour, surface
  override and shadow mode (about 100 B per static entity, no vertex work). *Hearthvale* darkens a
  watered tile through its colour alone, which is why the compare covers more than the transform
  (its plan's E2). A change rebakes that one cell the next frame. A moved transform also warns once
  that "a Static entity moved"; a colour or mesh change is expected and doesn't. Adding, removing or destroying a static entity marks its cell dirty.
- **Direct API**: `Renderer3D::CreateStaticBatch(StaticBatchParams)` takes meshes, transforms and
  keys and returns a `StaticBatch` handle. `SubmitStaticBatch(handle, transform)` covers games
  outside the ECS.

### 2.7 Skinned throughput

- **Palette arena**: all palettes for the frame go into one storage-buffer arena, uploaded once,
  each draw indexing its palette by a base offset (the v0.8 deferral). This retires the volatile
  `SkinData` UBO's write budget. `MaxSkinnedInstances` stays as a budget, but its ceiling moves
  from 256 to what the arena holds (default 1024). The `SkinData` block stays declared for custom
  skinned shaders, which keep working through the old path.
- **Culling**: §2.2. A culled skinned mesh is neither drawn nor uploaded.
- **Animation LOD**: `AnimatorComponent::CullingMode { AlwaysAnimate, PauseWhenCulled,
  ReduceWhenCulled }`, default `AlwaysAnimate`, so nothing changes until a game opts in.
  - A culled animator still advances its time and fires its events, because events are gameplay.
    It only skips sampling and composing the pose.
  - `ReduceWhenCulled` evaluates every 4th frame.
  - Sockets and physics read the last evaluated pose, so a sword parented to a culled hand lags at
    most 3 frames off screen, which nobody sees.
- **Instanced skinning** (the same mesh with different palettes, as one draw) is the natural next
  step once palettes live in an arena. It is a **stretch goal** for P5: crowds are not a v1.0 game's
  need.

### 2.8 DingoUI: the game UI framework (workstream U, closes #98)

**The plan of record is `.claude/plans/2026-10-08-v1.0-game-ui-plan.md`**, the full DingoUI design
(also published as https://claude.ai/artifact/EksE543uHba3XwcNe4aTSy). Its decisions D1–D8 are
settled; this plan cites them as **UI-D1–UI-D8** to keep them apart from its own D1–D10. This
section only says how DingoUI fits into v1.0.

- **What it is**: `DingoUI`, an immediate-mode UI for game HUDs and menus
  (`DingoUI::Button("Play")`). It has focus navigation for keyboard and gamepad, world-space UI,
  9-slice skins and themes, and tweens and screen transitions, and it hides the clicks it takes from
  the game. ImGui stays the debug UI.
- **Why in v1.0**: every example builds its HUD and menus by hand from sprites and text
  (*Marionette*'s `Hud.cpp` and `Screens.cpp` are 342 lines, *Candlewick*'s `Hud.cpp` 232).
  `Dingo::UI` is an ImGui facade for debug panels, and a release game lives in its menus.
- **Why it runs in parallel**: DingoUI has its own batcher and shader, and draws onto the swap chain
  after the game's drawing and the post chain. It shares no code with Renderer3D, so workstream U
  doesn't wait on, or block, the throughput phases P2–P6 (§3.1).
- **What it touches in the engine**: `Application::Run` (a `BeginFrame` before any `OnUpdate`, an
  `EndFrame` before ImGui), `Input` (a private consume mask), `Font` (line metrics and `MeasureText`
  with wrap, shared with `Renderer2D::DrawText`) and `Scene` (`WorldToScreenPoint`). All of that is
  its U0 (the DingoUI plan's §3).
- **Who builds on it**: *Hearthvale*, the 1.0 release game (§6), builds its menus and HUD on DingoUI
  **once U5 (focus navigation) lands**. Its pad-first menus need that phase. Until then its early
  milestones use text HUDs.

### 2.9 Stability

- **Bug sweep** (P1): fix #137 (#145, #144 and #109 were fixed on master by #148, #109 as D9
  says: Vulkan by default), and *Hearthvale*'s E1: the model loader
  drops material base colours (`Model.cpp:160-172`), so a colour-only pack loads white.

  pass it as the mesh colour; vertex colours stay out, since the vertex layout is frozen. Then the 11 open v0.8.0 Lows (each fixed, or closed
  with a reason) and v0.9's DX11 `Particles` timer. P0 added one: the Vulkan debug callback moves
  from `VK_EXT_debug_report` to `VK_EXT_debug_utils`, since sync-validation messages never reach
  the old one (§9 "P0 Part B"); without it, "sync validation clean" can't be read from `Dingo.log`.
- **Logs**: `Dingo.log` moves from the cwd to `GetUserDataDir(<app name>)/logs/`, keeping the last 5
  runs. A shipped game in `Program Files` can't write beside itself, and a player's bug report needs
  last session's log, not an empty truncated one. `ApplicationParams::LogDirectory` overrides it.
  The examples keep a `--log-here` flag.
- **Crashes**: `Internal::CrashHandler`, installed in `Application::Initialize`.
  - **Windows**: an SEH filter writes a minidump (`MiniDumpWriteDump`, `dbghelp`) beside the log,
    flushes spdlog, and shows one message box.
  - **Linux**: `sigaction` for SIGSEGV, SIGABRT, SIGFPE and SIGILL writes `backtrace_symbols_fd` into
    the log.
  - **Both**: `std::set_terminate`.
  - **`DE_VERIFY`**: in Distribution it stops breaking and calls a `FatalError(message)` that logs,
    shows the box and exits with code 1. A crash with no message is the worst thing a shipped game
    can do.
- **Automated checks**:
  - **Windows CI** runs the test app's checks on **WARP**, on DX11 and DX12. The VM notes show WARP
    runs every case, though its timings mean nothing. The script is a PowerShell twin of
    `linux-smoke-test.sh`, with the same `[FAIL]`/`LOG ERROR` rules.
  - **Linux CI** adds a Debug-ASan job with leak detection on, and suppressions for the libxcb and
    Mesa leaks already found (`LINUX-SUPPORT.md:304`).
  - **Both CIs** run `Marionette --tournament=10 --seed=1 --player-tier=3`, its result fixed by
    `719df64`.
- **Unit tests** (D6): a small headless `Dingo-UnitTests` project covering pure code: `Frustum`,
  `LightMath`, `Utf8`, `UUID`, the `.events` parser, `ShadowAtlasAllocator`, tone-mapping curves
  and the save-data format. It runs in both CIs before anything windowed.
- **Soak**: `scripts/soak.sh` (and a `.ps1` twin) runs *Marionette*'s tournament and *Candlewick*'s
  autoplay for 60 minutes each. It logs the resident set every minute and fails on growth past 5%
  after the first 5 minutes. This runs on the GPU machine at P10, not in CI.

### 2.10 The API pass (D7, D8)

A header-by-header audit of `include/DingoEngine` (102 headers) produces
`.claude/reviews/<date>-v1.0-api-review.md`. Each finding is keyed `A*` and gets a verdict: keep,
change before 1.0, or deprecate. These are known going in:

| Item | Proposal |
|---|---|
| #109 no default `GraphicsAPI` | Done on master (#148): Vulkan by default (D9) |
| `DirectionalLightComponent::Ambient` (legacy since v0.7) | Keep with the same look; mark `[[deprecated]]` with a message pointing at `AmbientLightComponent`, removal in 2.0 |
| Inherited visibility | `Entity::SetActive(bool)` / `IsActiveInHierarchy()`: an inactive entity and its subtree don't render, simulate, animate, play audio or run scripts. Its physics bodies are removed and re-added (v0.8 deferral) |
| `Destroy()` vs `delete` pairing, `Create()` factories that do or don't initialize | One rule, written down in `docs/conventions.md` |
| Fixed step | `ScriptableEntity::OnFixedUpdate(step)`, driven by the same accumulator the 3D physics step already computes. It is the seam networking and deterministic gameplay need (`ROADMAP.md:425`) |
| Body-to-entity lookup (#102, part) | `Scene::GetEntityForBody3D/2D`. Casts already return bodies, and every game maps them back by hand |
| Commented-out test cases (`TestLayer.cpp:51-55`) | Delete them, or revive each as a check |
| `Internal::` | Everything a public header has to name but games mustn't use moves under `Dingo::Internal`, which `docs/versioning.md` excludes from SemVer |

**Versioning promise** (`docs/versioning.md`): after 1.0.0, a minor release adds and a patch release
fixes. Breaking a public header needs 2.0, and a deprecation lives through at least one minor
release. Behaviour that looks different counts as a break unless it fixes a filed bug.

**API reference** (D7): Doxygen run over `include/` in CI and published to GitHub Pages, with
`docs/*.md` pulled in as its guides. The header comments a reference needs collide with CLAUDE.md's
comment rule, so D7 decides between two options:

- relax the rule for public headers only: one `///` line per public type and function, saying what
  it promises;
- keep headers bare and generate the reference from signatures plus the guides.

### 2.11 What a shipped game needs from the engine (D1)

*Hearthvale* (§6) ships on these, and so would anyone else's game:

- **Game UI** (#98): **DingoUI**, its own workstream (§2.8, §3.1). A builder lives in its menus
  (build palette, inventory, shop), so *Hearthvale* is its first full user.
- **Save data**: `SaveData`, a typed key/value tree (bool, int, float, string, `vec*`, nested
  objects, arrays).
  - It is written as JSON to `GetUserDataDir(<game>)/saves/<slot>.json`.
  - Writes are atomic (a temp file, then rename) and keep one `.bak`.
  - The JSON library is hidden behind the API (D10).
  - `Settings` is a ready-made `SaveData` slot holding display, audio and input settings.
  - **No scene serialization in v1.0**: games save their own state. A full scene format is post-1.0,
    together with an editor.
- **Done on master** (#110, merged into `feat/v1` 2026-10-09), so P8 doesn't build them:
  - **audio buses** (#95): `AudioEngine::CreateBus(name, parent)`, sub-buses, `k_MasterBus`
    (docs/audio.md). Games create their own buses; there are no named defaults besides `Master`;
  - **runtime VSync** (#87): `Window::SetVSync/IsVSync`, applied with the pending resize;
  - **fog** (#92): `Renderer3D::SetFog/ClearFog`, `FogComponent`, scene-scoped, off by default;
  - **translucent 3D** (#91): `MaterialParams::Translucent`, a far-to-near sorted pass after opaque
    (skinned meshes too) that the shadow pass also draws.
- **Display modes** (the rest of the old #87 item): a resolution and display-mode list for an
  options screen. Fullscreen already toggles.
- **Out of v1.0** unless the game proves it needs them: root motion (#104), event payloads (#103),
  sensors and cast filters (the rest of #102), controller-against-controller collision (#101).
  They are filed, and each takes a day or two when needed.

### 2.12 Platform and shipping

- **Linux**: run L26 on real hardware (the owner's machine, or a USB-booted Ubuntu on the GPU
  machine), using the tester bundle that already exists.
  - L27 (native Wayland): recommended **no** for 1.0. XWayland runs GLFW's X11 build on every
    desktop that matters, and native Wayland changes window decorations and cursor locking.
  - The first real run of the Linux release job is the **v1.0.0-rc.1** tag.
- **macOS**: out of scope, stated in the README. MoltenVK plus Metal-specific swap-chain and GLFW
  work is a module-sized job with no user asking for it.
- **#74** (a display on another GPU) closes as `wontfix` for 1.0, documented. **#73** stays `wontfix`.
- **Licences**:
  - `THIRD-PARTY-NOTICES.md`, generated from each vendor's licence file by
    `scripts/gather-notices.sh`, goes into every release archive and every packaged example.
  - Arial Bold and Arial Black are replaced everywhere by an OFL font (proposed: **Inter**, which
    covers Latin-1 and General Punctuation, everything the MSDF atlas bakes). Its OFL text ships
    beside it.
- **Executable metadata**: a Windows version resource and icon per example through premake
  (`files { "*.rc" }`), and a `.desktop` file plus icon in the Linux tarball.

### 3.2 Cloud or GPU machine

The dev routine runs in a cloud container: Linux and GCC, with **no GPU and no Windows**. With the
environment below, it can do everything Linux CI does:

- build every project;
- run the test app's checks, every example and the `--check` runs under Xvfb on **llvmpipe**
  (software Vulkan), with the validation layer and its sync validation.

It **can't**:

- compile or run D3D11 or D3D12: the Linux build leaves the D3D sources out;
- build Windows-only code (MSVC, SEH, `dbghelp`);
- take meaningful timings: llvmpipe rasterises on the CPU, and a shared container's CPU is noisy;
- use a real pad, speakers or display;
- judge a look on real hardware.

Every phase is labelled with one of three tags:

- **Cloud**: developed and finished in the cloud.
- **Cloud, GPU sign-off**: developed in the cloud. Its done-when includes a short run on the GPU
  machine: the 0 px gate on Vulkan, DX11 and DX12, its timings, or a first Windows compile of code
  the cloud can't build. These runs are batched (below), so they don't hold up the next phase.
- **GPU machine**: the work itself needs the GPU machine. The cloud can prepare code, but can't
  iterate on it.

## 4. Verification

- **0 px where nothing should change**, every phase. The scene set is:
  - the Lighting Test (`default`, `lights`, `overbudget`, `materials`, `--entities`);
  - `--test=batch`, `--test=mesh`, `--test=model`, `--test=anim --anim=clip --anim-time=0.5`;
  - the Shadow and Post Tests;
  - a frozen *Candlewick* room and a frozen *Marionette* pose.

  Each is compared against the previous phase **and** a deliberately broken build. Culling (P2),
  per-object data with no override (P3) and static bakes (P5) are held to 0 px. Instancing (P4) is
  held to the D2 tolerance against its own forced-CPU run.
- **Culling is conservative**: a check renders `mixed` with culling on and off and requires 0 px.
  A second check counts the meshes culled, so a cull that never culls doesn't pass.
- **Backends**: Vulkan, DX11 and DX12 on the GPU machine every phase. The DXBC path is where
  `SV_InstanceID` with a base offset and `ByteAddressBuffer` reads in the vertex stage go wrong, so
  P4 lands with a check on all three.
- **Timing**: every phase records its row of §2.1's table, plus *Candlewick* and *Marionette*
  `--perf`, Release and Debug, on all three backends. A phase that slows a scene it doesn't touch
  doesn't land.
- **DingoUI**: its own checks (`--test=dingoui`, the DingoUI plan's §5) on all three backends; a
  frame with no root must hold the 0 px gate on the regression set.
- **Validation**: Vulkan validation including **sync validation** (which found #145), the DX11 debug
  layer and the DX12 debug layer stay clean on every check.
- **On the VM**: functional checks on DX11 and DX12 (WARP) only, never timings.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Retained submission changes `SubmitMesh`'s timing: a game that mutates a mesh after submitting it now draws the mutated mesh | Documented. `Mesh` data is immutable during a scene; Debug asserts on a `Reinitialize` between `BeginScene` and `EndScene` |
| A conservative cull that isn't: an AABB that misses skinned extremes or a scaled-up child | Skinned bounds padded by half (the caster rule); culling on/off 0 px check; F4 freeze-frustum |
| Instancing differs per backend (base instance, `SV_InstanceID` starts at 0 on D3D even with a base) | The record base goes in a uniform, never `gl_BaseInstance`; checked on all three in P4 |
| The object buffer's extra vertex attribute breaks a custom shader | Custom materials keep the 48 B layout; the 52 B vertex is built-in only |
| Static change detection costs a compare per static entity per frame | 48 B memcmp × 10k ≈ 10 µs; measured in P5 |
| The crash handler itself crashes or deadlocks (spdlog's mutex held by the crashing thread) | The handler writes with `write(2)` and `WriteFile` into a preallocated buffer and tries spdlog's flush last |
| WARP or llvmpipe CI flakes on timing-based checks | CI checks are pixel and log based only; timings stay on the GPU machine |
| DingoUI's own risks | Listed with their mitigations in the DingoUI plan's §6 |
| Two workstreams in flight collide in `Application::Run` and `Input` | U0 lands first and alone; P-phases rebase onto it |
| The API pass breaks every example | Breaks are fixed in the same commit across all ten examples and the test app; the migration doc is written as they land |
| Scope (~44 engine days plus a release game) | Cut order in §3; the game starts on P2–P5 while P6–P9 land; its own plan sets a content target it can meet |
| A release game needs content the engine work doesn't produce (art, balance, music) | CC0 kits checked in H0; the content target is set in its plan, after the costs are known |

### P0 Part A (2026-10-08): the Throughput Test

Part B (the baselines on the GPU machine) ran on 2026-10-09; see the next section.

- **Built**: `test/src/Tests/Scene/ThroughputTest.*`, `--test=throughput`.
  - Modes: `--throughput=static|repeat|mixed|skinned|shadow`, `--count=N` (10000; `skinned` 64), `--seed=S` (1).
  - `static`: one prism `Mesh` per entity (3–9 sides, random radii, height and twist; ~36 vertices on average, 359,058 in all), in a grid.
  - `repeat`: five props (crate, pillar, torch, rock, barrel).
  - `mixed`: rooms of 10 × 10 cells walled by pillars with doorways, cells 45% floor tiles, then half unique prisms and half props. The camera flies a 1200-frame lap at 0.3 of the layout's side and sees 0.5 of it ahead, so **9.4%** of entities are in view on average (logged as `visible_pct`).
