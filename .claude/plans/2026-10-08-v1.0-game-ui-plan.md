## 2. Design

### 2.1 Shape: immediate API, cached state (D1)

Games describe the UI every frame from `OnUpdate` or a script's `OnUpdate`; the engine lays it out,
draws it and keeps per-element state between frames:

```cpp
using namespace Dingo;

if (DingoUI::BeginRoot("pause", UIRootParams().SetAnchor(UIAnchor::Center).SetModal(true)))
{
    DingoUI::Text("Paused", UITextStyle::Title);
    if (DingoUI::Button("Resume").Clicked) m_Paused = false;
    if (DingoUI::Button("Options").Clicked) m_Screen = Screen::Options;
    DingoUI::Slider("Volume", m_Volume, 0.0f, 1.0f);
    DingoUI::EndRoot();
}

DingoUI::ProgressBar("hp", m_Health / m_MaxHealth, UIBoxParams().SetSize(UISize::Fixed(240), UISize::Fixed(18)));
```

- **Nothing to own, nothing to dangle.** No widget objects, no callbacks capturing `this`. The
  engine's recurring bug class (a cached pointer outliving its object) has no surface here.
- **Ids** are an FNV-1a hash of the label (text after `##` is id-only, ImGui's convention) mixed with
  an id stack (`PushId`/`PopId`, implicit per root and container). Ids are 64-bit; a collision in one
  frame warns once in Debug.
- **State** (hover/press/focus, tween values, scroll offset, appear time) lives in an id-keyed map in
  the context and is dropped after an element goes unseen for 2 frames (exit tweens excepted, §2.7).
- **Results** are a small value: `UIInteraction { Hovered, Pressed, Down, Clicked, Focused, HoverT }`.

### 2.2 Frame flow and latency

`DingoUI` is a static class in `Dingo` (`include/DingoEngine/UI/DingoUI.h`), the way `Renderer2D` and
`Input` are; its helper types carry a `UI` prefix (`UIAnchor`, `UIRootParams`, `UIStyle`,
`UIInteraction`). The state behind it is one engine-internal `Internal::DingoUIContext`, created when
`ApplicationParams::DingoUI.Enabled`, default on (it costs nothing while no element is declared).

1. **`BeginFrame`** (in `Application::Run`, after `AssetManager::Update`, before any `OnUpdate`):
   take the input snapshot, hit-test it against **last frame's** element rects, resolve hover /
   press / click / focus moves, and consume what the UI took (§2.4).
2. **Declare** — every layer's `OnUpdate` calls widgets. Each call appends a node to a per-frame arena
   and returns the interaction resolved in step 1 for that id.
3. **`EndFrame`** (after the last `OnUpdate`, before ImGui): lay out (§2.3), build vertices (§2.5),
   draw into the swap chain after everything the layers drew, so the UI sits over the post chain's
   output and is never tone-mapped.

Hit-testing uses the previous layout, so a widget that moved this frame reacts one frame late — the
standard immediate-mode trade (Clay and ImGui both make it). In exchange interaction is known
*before* game code runs, which is what makes consumption work.

### 2.3 Layout: a flexbox subset, two passes

- **Roots** anchor to the viewport: 9 anchor points + `Stretch`, a pixel offset, and a pivot. Roots
  draw in declaration order; `SetLayer(int)` overrides.
- **Containers**: `Direction` (row/column), `Gap`, `Padding`, `Align` (main + cross axis), child
  sizing per axis `Fixed(px)` / `Fit()` (default) / `Grow(weight)` / `Percent(f)`, with min/max.
- **Algorithm**: fit sizes bottom-up, grow/shrink top-down, then positions — linear in node count,
  no allocation (arena reset each frame). Text measures through the new Font metrics (§3.1) and wraps
  at the width its parent grants (a second fit pass for wrapped text only, as Clay does).
- **Scaling**: `ScaleMode::ConstantPixel` or `ScaleWithScreen(reference 1920×1080, match 0..1
  width↔height)`, so a HUD keeps its proportions at 720p and 4K. Applied as one factor at layout.
- **Pixel snapping** of final rects, so 1-px borders stay crisp.

### 2.4 Input consumption (#98's real ask)

- In `BeginFrame`, a press over any element of a root that blocks input (every root by default;
  `SetBlocksInput(false)` for a pure HUD) is **consumed**: `Input::IsMouseButtonPressed/Down/Released`
  report false to game code for that button until it's released, and the scroll delta reads zero
  over a scroll area. Implemented as a private consume mask inside `Input`'s snapshot, set by the
  context — no new public Input calls (D6).
- `DingoUI::IsPointerOverUI()` / `IsCapturingKeyboard()` for games that want to ask.
- Events: the context sits behind an engine overlay layer under ImGui's, which marks
  `MouseButtonPressedEvent`/`MouseScrolledEvent` `Handled` when they land on a blocking rect.
- ImGui wins: while ImGui's `WantCaptureMouse`/`WantCaptureKeyboard` is set, the game UI sees no
  input. That also fixes debug panels leaking clicks into games today (worth its own `bug` issue).
- A **modal** root consumes all pointer input and focus navigation, wherever the pointer is.

### 2.5 Rendering: one shader, usually one draw (D7)

Renderer2D's quad/circle/text split would cost a `Flush` every time a panel lands on text (a modal
over a HUD), so the UI gets its own small batcher inside the engine (`src/DingoEngine/UI/DingoUI/`):

- **One vertex format**: position, UV, colour, rect-local coords, corner radius, border width,
  texture index, a kind (solid / textured / MSDF glyph), and the **clip rect** (§ below).
- **One fragment shader** (`DingoUI.glsl`, embedded like `Renderer3D_Lit.glsl`): rounded rectangles
  and borders as an SDF (crisp at any scale, no textures), textured quads, MSDF glyphs from the
  font atlas. Kind is a per-vertex branch — uniform within a quad, cheap.
- **Clipping in the shader**: each vertex carries its clip rect, the fragment discards outside it.
  No scissor API, no draw split per scroll area. Fully clipped quads are culled on the CPU.
- **Draws**: one per 32-texture window (fonts + images); a typical menu is one draw call.
- **Cache**: the built vertex stream is hashed; an identical frame skips the rebuild and the upload
  (non-volatile vertex buffer, so the "write every frame you bind" rule for volatile buffers doesn't
  apply). A static HUD costs a hash and one draw.
- **Budget** (checked in U8): < 0.1 ms CPU for a 500-element menu on the dev machine, and *Marionette*'s
  HUD no slower than its hand-drawn version (measured old vs new, same frame).

### 2.6 Widgets and styling

- **v1 widgets**: `Box`/container, `Text` (wrap, align, colour runs out of scope), `Image` (texture,
  UV rect, tint, 9-slice), `Button`, `Toggle`, `Slider` (float/int), `ProgressBar`, `Spacer`,
  `ScrollArea` (vertical), `Selectable` (list rows). Each is a few lines over the layout + interaction
  core, so games can build their own with `Box` + `GetInteraction(id)`.
- **Style**: a `Style` struct (fonts and sizes per `TextStyle`, palette per widget state, padding,
  gap, corner radius, border, optional `NineSlice { Texture*, insets }` per widget kind), set
  engine-wide from `ApplicationParams::DingoUI.Style` and overridden with `PushStyle`/`PopStyle` or a
  per-call `BoxParams`. The default theme ships with the engine font so a game draws something
  sensible with zero setup.
- **9-slice**: 9 CPU quads from one texture; centre `Stretch` or `Tile`.

### 2.7 Tweens and transitions

- Per-id state carries `HoverT`, `PressT`, `FocusT`, `AppearT`, eased on the **real** delta (UI keeps
  animating while a game pauses its scene). Style values can name a target per state; the widget
  lerps colour/scale by those Ts. Durations in `Style`.
- **Screen transitions**: `RootParams().SetTransition(Transition::Fade(0.2f) | Slide(...))`. Entry
  is driven by `AppearT`. Exit needs the root's *last* declared output after the game stops
  declaring it: the context keeps each transitioning root's final vertex range for the exit duration
  and plays it out. Exiting roots never take input.

### 2.8 Focus navigation (keyboard and gamepad)

- Focusable widgets register in their root's **focus scope**. Arrows / D-pad / left stick (with
  repeat) move focus spatially to the nearest rect in that direction (last frame's rects);
  `Confirm` = Enter, Space, pad A; `Back` = Escape, pad B → `DingoUI::IsBackPressed()`.
- `SetDefaultFocus()` on a widget picks the start; focus is restored per root when it reopens.
- Focus visuals show only after a navigation input; moving the mouse hands control back to it.
- An active focus scope consumes the inputs it uses, like the pointer does (§2.4).
- Bindings in `Style`/params so a game can remap; no text entry in v1 (D8).

### 2.9 World-space UI

- New `Scene::WorldToScreenPoint(worldPos, viewportSize)` (mirror of `ScreenPointToRay`, perspective
  and orthographic), returning `std::optional<glm::vec2>` (none behind the camera).
- `BeginWorldRoot(id, scene, worldPos, params)` anchors a root at that point with a pivot (health bar
  above a head, a name label), optional distance scaling and a max distance; roots behind the camera
  are culled. World roots draw below screen roots and never block input unless asked.
- Out of scope: diegetic panels in 3D with depth testing (a render-to-texture of a root onto a mesh is
  possible later with v0.8.3's `SceneRenderer::Render(scene, target)` path).

### 2.10 Tooling

- **F9 "UI" tab**: roots, element count, draw calls, layout and build µs, cache hit, hovered/active/
  focused id, plus a "show rects" overlay drawing every element's rect and id.
- `DE_PROFILE_*` zones on `BeginFrame`/layout/build and a GPU pass timer `DingoUI` in F8.
- Test framework: **DingoUI Test** (`--test=dingoui`, `--dingoui=layout|widgets|focus|world|stress`) with
  PASS/FAIL checks. The context takes a plain `UIInputState` struct (the engine fills it from
  `Input`), so the checks drive clicks and navigation without real devices.

### 2.11 Out of scope

Text input and IME, rich text (inline colour/icons), localisation and right-to-left text, docking,
a visual editor, data-driven layout files (decided against in D2; can follow as a module), replacing
ImGui for the debug panels (D2), diegetic 3D panels with depth.

## 3. Groundwork the engine needs first

### 3.1 Font metrics

`Font::GetLineHeight(size, lineSpacing)`, `GetAscender(size)`, `GetDescender(size)` and
`Font::MeasureText(str, size, maxWidth, kerning) → TextMetrics { width, height, lineCount }` with the
wrap breaks the layout and the batcher share (UTF-8 through `Graphics/Utf8.h`, the decoder
`DrawText` uses). Renderer2D's `DrawText` gains `TextParameters::MaxWidth` on the same code, so the
two never disagree.

### 3.2 World → screen

`Scene::WorldToScreenPoint` (§2.9), in `CameraUtils` beside the ray code.

### 3.3 Input consume mask

Private `Input::ConsumeMouseButton/ConsumeScroll/ConsumeKey/ConsumeGamepadButton`, cleared when the
button is released; public queries respect it. Friend access from the context only.

## 6. Risks

| Risk | Mitigation |
|---|---|
| One-frame hit-test latency feels laggy on a widget that just appeared | Interaction only uses rects of elements that existed last frame; newly appeared widgets ignore the press that frame (no misfire). Fine at 60 fps; Clay ships this |
| Id collisions from duplicate labels in loops | `PushId(i)` in docs and examples; Debug warns on a same-frame collision |
| Consuming input breaks a game that reads the mouse under a HUD | HUD roots can `SetBlocksInput(false)`; consumption only on rects, never the whole screen unless modal |
| Exit transitions in an immediate API | Keep the root's last vertex range, not its tree: no re-layout, no input, bounded memory |
| MSDF text in a second batcher drifts from Renderer2D's | Both lay glyphs out through the shared §3.1 code |

## 7. Decisions

Settled 2026-10-08 by the user:

- **D1** Immediate-mode API with cached per-id state (not a retained tree, not ECS components).
- **D2** Scope: game HUD and menus. ImGui stays the debug UI; no layout files.
- **D3** v1 includes focus navigation, world-space UI, 9-slice + themes, and tweens/transitions.
- **D4** Part of the v1.0 milestone, not its own version or a module.
- **D5** Named **`DingoUI`**: a static class in `Dingo` (`DingoUI::Button(...)`), like `Renderer2D` and
  `Input`, so the "everything in `Dingo`" convention holds. `Dingo::UI` stays the ImGui facade.

Settled 2026-10-08 as recommended:

- **D6 Consumption default.** Consumed presses are **hidden from `Input` by default** (what #98
  asks), with `IsPointerOverUI()` for games that want the raw picture.
- **D7 Clipping.** **Shader-side clip rects** (one draw for a whole menu) over a new scissor
  API (a draw per clip change).
- **D8 Text entry.** **Out of v1** (needs char events, IME and caret handling); a name-entry
  field can follow on request.
