## 2. Design

### 2.1 Scene UBO: freeze the prefix, append the lights

The first 96 bytes stay exactly as they are, so every existing custom material compiles and renders
unchanged. A shader may declare a shorter block than the buffer bound to it, on Vulkan and on D3D. New
fields are appended after the prefix:

```glsl
layout(std140, binding = 0) uniform CameraData
{
    // Frozen prefix (v0.4.2–v0.6). Custom materials may declare only these three.
    mat4  ViewProjection;
    vec4  LightDirection;    // primary directional light, legacy
    vec4  Ambient;           // x = legacy ambient scalar
    // v0.7
    vec4  CameraPosition;    // xyz
    vec4  AmbientColor;      // rgb = colour × intensity, summed
    ivec4 LightCounts;       // x = directional, y = local (point + spot)
    DirectionalLight Directional[4];  // { vec4 Direction; vec4 Color /* rgb × intensity */ }
    LocalLight       Lights[32];      // 48 B each, see below
};
```

`LocalLight` packs point and spot into one type, so they share a single budget:

| vec4 | xyz | w |
|---|---|---|
| `PositionRange` | world position | range |
| `Color` | colour × intensity | spot `scale` |
| `SpotDirection` | world direction | spot `offset` |

Spot factor = `saturate(dot(-L, dir) * scale + offset)²`, with
`scale = 1 / max(cosInner - cosOuter, 1e-4)` and `offset = -cosOuter * scale`. A point light uses
`scale = 0, offset = 1`, so it runs the same branch-free code. Size is about 1.9 KB, far under every
backend's constant-buffer limit.

The legacy prefix stays populated. `LightDirection` comes from the first directional light, and
`Ambient.x` from that light's legacy `Ambient`. The DC3D and EchoVault shaders keep seeing what they
see today.

### 2.2 Shading model (the lit shader)

- New varying `v_WorldPos` (free, because `a_Position` is already world-space) plus `v_TexCoord`.
- `color = albedo * (AmbientColor + Σ diffuse) + Σ specular * Specular + emissive`.
- **Diffuse**: Lambert per light.
- **Specular**: Blinn-Phong, exponent mapped from `Roughness` (`exp2(10 * (1 - r) + 1)`, range
  2–2048). This is cheap and predictable while the frame still clips (no tone mapping until v0.9).
  The parameter names (`Roughness`, `Specular`) outlive a later GGX swap.
- **Falloff**: `saturate(1 - (d / range)²)²` (decision D4). `Intensity` is the brightness at
  the light, and `Range` is exactly where it reaches zero. That is art-friendly, and it makes
  range-sphere culling exact.
- Loops are bounded by `LightCounts`. Check that FXC doesn't unroll 32 iterations on the D3D path
  (SPIRV-Cross output → DXBC); watch compile time and add `[loop]` if needed.

### 2.3 Renderer3D API (non-ECS users get everything too)

Selection lives in `Renderer3D`, not in `SceneRenderer`, so hand-driven passes such as
`MeshColliderTest` and non-ECS games also get culling and the light budget.

```cpp
struct DirectionalLight { glm::vec3 Direction; glm::vec3 Color{ 1 }; float Intensity = 1.0f; };
struct PointLight       { glm::vec3 Position;  glm::vec3 Color{ 1 }; float Intensity = 1.0f; float Range = 10.0f; };
struct SpotLight        { glm::vec3 Position;  glm::vec3 Direction; glm::vec3 Color{ 1 };
                          float Intensity = 1.0f; float Range = 10.0f;
                          float InnerConeAngle = 20.0f; float OuterConeAngle = 30.0f; }; // half-angles, degrees

void BeginScene(const PerspectiveCamera&);         // camera position from the camera
void BeginScene(const glm::mat4& viewProjection);   // camera = inverse(VP) * (0,0,1,0), dehomogenised (w = 0: ortho)
void SetAmbientLight(const glm::vec3& color, float intensity);  // scene-scoped, replaces
void SubmitLight(const DirectionalLight&);                      // scene-scoped
void SubmitLight(const PointLight&);                            // P2
void SubmitLight(const SpotLight&);                             // P2
void SetDirectionalLight(const glm::vec3&, float);  // now sets the default (fallback) light
```

*As built in P1:*

- The structs live in `include/DingoEngine/Graphics/Light.h`. A public
  `BeginScene(vp, cameraPosition)` was not needed: deriving the position from `inverse(VP)` is exact
  for perspective cameras.
- Lights and ambient are scene-scoped. Whatever was submitted since the last `EndScene` (before or
  after `BeginScene`) lights the next one, which then clears it, so the old "set the light, then
  `BeginScene`" order still works.
- The legacy prefix (`LightDirection`, `Ambient.x`) can't express "no sun". In a scene with no
  directional light it carries the default light's direction, so a custom shader using the old
  `a + (1-a)·N·L` formula draws a sun the lit shader doesn't. Document this in P6, and point custom
  shaders at the full block.
- `v_WorldPos` moved to P2, where it is first read.
- The scene-UBO upload moved from `BeginScene` to the top of `EndScene`, after the lights are
  resolved and before the first draw.
- **Fallback light**: if a scene submits **no light of any kind and no ambient**, `Renderer3DParams`'
  default light is used. It is emitted as ambient `a` plus one white light of intensity `1 - a`,
  which matches the pre-v0.7 image pixel-for-pixel. A scene with only point lights gets no sun (the
  dark-keep case). A scene that wants pitch black submits `SetAmbientLight(black, 0)`.
- **Directional cap**: a fixed `Renderer3D::k_MaxDirectionalLights = 4`, with no runtime cap.
  Overflow warns once, counts in `Statistics::DroppedLights`, and honours `AssertOnOverflow`.
  P2 adds `MaxLights` (local lights) to `Renderer3DCapabilities`.
- The fragment stage now reads binding 0 too. `NvrhiShader::CreateBindingLayoutHandle` therefore
  de-duplicates bindings reflected by more than one stage.

### 2.4 Light selection (in `EndScene`)

1. Frustum planes from `ViewProjection` (Gribb–Hartmann; depth is [0,1] workspace-wide).
2. Drop local lights whose `(position, range)` sphere is outside the frustum, or that have
   `Intensity <= 0` or `Range <= 0`.
3. Score = `max(Color.rgb) * Intensity / (1 + max(0, dist(camera, light) - range)²)`. A light whose
   range contains the camera scores at full intensity.
   - *As built in P2:* the score uses the strongest channel, not luminance. The over-budget test
     showed luminance making a pure-blue light about 10× "dimmer" than an equal green one, which
     overrode distance and dropped the lights nearest the camera.
4. `std::partial_sort` to `MaxLocalLights`, **tie-broken by submission index**. Registry iteration
   order is stable frame to frame, so an unchanged scene selects identically every frame, with no
   flicker. Two runs of the over-budget test were pixel-identical.
5. Directional lights are not culled: the first `k_MaxDirectionalLights` in submission order.
6. On overflow, `Statistics::DroppedLights` is set and a WARN is logged.
   - *As built:* the WARN fires once per renderer lifetime, not once per onset. A camera hovering
     at the budget edge would otherwise log every frame.
   - The F4 panel shows the count (P5).
   - Popping at the budget edge is a **documented limitation**; a rank-fade band is deferred.
   - *As built in P5:* the F4 Renderer tab has a "Renderer3D lights" block: directional `n / 4`, a
     point/spot bar against `Renderer3D::GetLocalLightBudget()` (new, also used by
     `ResolveSceneLights`), out of view, and dropped in red. `DroppedLights` counts both kinds, so
     the label says "past a light limit" and defers to the log. Lights rejected as unusable
     (intensity or range ≤ 0, non-finite) are counted nowhere; a later "invalid" counter could.
7. *As built:* the Lighting Test (`--test=light`, modes `--lighting=default|lights|overbudget`)
   landed in P2 as its verification harness. P4 adds the specular sphere row and P5 the F4 stats.

### 2.5 ECS

```cpp
struct DirectionalLightComponent { glm::vec3 Direction{ -0.4f, -1.0f, -0.35f };
                                   glm::vec3 Color{ 1.0f }; float Intensity = 0.65f;  // D2: today's look
                                   float Ambient = 0.35f; };                           // legacy, D1
struct PointLightComponent   { glm::vec3 Color{ 1.0f }; float Intensity = 1.0f; float Range = 10.0f; bool Enabled = true; };
struct SpotLightComponent    { glm::vec3 Color{ 1.0f }; float Intensity = 1.0f; float Range = 10.0f;
                               float InnerConeAngle = 20.0f; float OuterConeAngle = 30.0f;
                               glm::vec3 Direction{ 0, 0, -1 };  // local, rotated by Transform3D
                               bool Enabled = true; };
struct AmbientLightComponent { glm::vec3 Color{ 1.0f }; float Intensity = 0.1f; };     // D1
```

- Point and spot lights take their position (and the spot its rotation) from
  `Transform3DComponent`. Entities without one are skipped. v0.8's hierarchy then makes "a light on a
  lantern" plain parenting.
- `Enabled` exists because *Candlewick* snuffs and relights a lantern constantly, and zeroing
  `Intensity` would make game code store the old value.
- Gathering is a new engine-internal system `src/DingoEngine/Scene/Systems/LightSystem.{h,cpp}`
  (EnTT stays inside `src/Scene/`), exposed as `Scene::SubmitLights(Renderer3D&)`, which is public
  for custom passes like `RenderEntities3D`. `SceneRenderer.cpp:56` switches to it.
  `GetFirstDirectionalLightEntity` stays.
- Registration checklist for each new component: `DE_INSTANTIATE_COMPONENT` (`Entity.cpp:104-124`)
  and `Scene::DuplicateEntity` (`Scene.cpp:86-104`). No runtime handles, so no
  `ClearRuntimeHandles` or `ResetRuntimeHandles` entries.

*As built in P3:*

- **D2, refined after review:** `DirectionalLightComponent::Intensity` defaults to **1.0**. The
  legacy `Ambient` both adds white ambient and scales the light by `(1 - Ambient)`.
  - This is exactly the old `a + (1-a)·N·L` for **any** `Ambient`, not only the default 0.35.
    Fixing `Intensity` at 0.65 would have changed games that tuned only `Ambient`.
  - Setting `Ambient = 0` makes `Intensity` unscaled, for scenes that use
    `AmbientLightComponent`.
  - Only the first `k_MaxDirectionalLights` add ambient.

- **Default-light rule:** `LightSystem` submits a default `DirectionalLightComponent` when the
  registry has **no light component at all**. Any light component, even a disabled one or one
  with no `Transform3DComponent`, switches that default off.
  - It always calls `SetAmbientLight`, even with black. A scene whose lights are all switched off
    therefore goes dark instead of hitting Renderer3D's own fallback.
  - `SceneRenderer` no longer touches Renderer3D's default light.
- **Verification:** the Lighting Test gained "Lights as entities" (`--entities`). The entity path
  is pixel-identical to the direct API for the default and over-budget modes. Point+spot differs
  by 1 pixel at 1/255, from summation order.
- **Pulled forward from P6:** DungeonCrawler3D gained an opt-in `--night` and `--seed=<n>`, used
  as P3's visible before/after.
  - `--night` adds a dim moon, a "Lantern" entity moved above the hero in `UpdateCamera`, and a
    point light per treasure. The lantern can't sit at the body's centre: it would be inside the
    hero's mesh and leave it unlit. It becomes a child entity in v0.8.
  - `--seed` reproduces the first dungeon only.
  - The default look is unchanged.

### 2.6 Lit materials: specular, emissive and albedo on any material

Today only the one default material gets its binding-1 data written (`Renderer3D.cpp:157-160`), so
emissive on any other material is dead — the "surprising but correct" note in `KNOWN-BUGS.md`. v0.7
fixes this generally:

- `MaterialParams` gains `Roughness` (0.5) and `Specular` (0.0, per D2).
- `Renderer3D::GetLitShader()` and `GetDefaultMaterial()` become public. **Any** material whose
  shader is the lit shader gets its binding-1 `LitMaterialData { Emissive, Roughness, Specular }`
  written by `Renderer3D` every frame. This must happen every frame: NVRHI rejects binding a volatile
  constant buffer that wasn't written this frame (`Renderer3D.cpp:153-156`).
- Albedo map: the lit shader samples texture slot 0 (binding 2) and sampler slot 0 (binding 3),
  multiplied into the vertex colour. `Renderer3D` fills empty slots with the white texture and the
  default sampler, so the binding set still matches reflection exactly. **This lets Gloomdelve
  delete its hand-written night-lighting shader**, the workaround the roadmap text names.
- Per-mesh (vertex-attribute) surface parameters are **out of scope**. Batching stays per
  `Material*`; v1.0 material sharing is where that problem gets solved.

*As built in P4:*

- **`Renderer3D::CreateLitMaterial(MaterialParams)` replaces a public `GetLitShader()`.** It sets
  the shader and `CullMode::None`, which avoids the trap that `MaterialParams` culls back faces by
  default while front-face winding differs between Vulkan and D3D. `GetDefaultMaterial()` is
  public.
- **`EndScene` prepares every drawn lit material, every frame.** `PrepareLitMaterial` runs before
  its draws: it fills empty texture/sampler slot 0 with white and the clamp sampler, and writes
  binding 1 as `{ EmissiveColor; Surface = (emissive strength, roughness, specular) }`. This moved
  from a default-material-only write in `BeginScene`.
- **Specular** is normalised Blinn-Phong: `(n+8)/(8π)·(N·H)^n·N·L`, with
  `n = exp2(10(1-r)+1)`. It is skipped entirely when specular is 0, so non-shiny materials stay
  bit-identical.
  - Verified: the existing Lighting Test modes and the batch test match P3. The batch test's 3D
    view also matches the pre-v0.7 baseline.
- **Lighting Test:** a "Materials" mode (`--lighting=materials`, `--specular=off`) with a roughness
  row, an emissive lamp holding a point light, and a textured crate.

### 2.7 The lit shader as a file (hot-reloadable in dev, embedded when shipped)

Decision D3.

- Source of truth: `src/DingoEngine/Graphics/Shaders/Renderer3D_Lit.glsl` (the normal
  `#type vertex` / `#type fragment` format).
- **Build**: a premake custom build rule on `src/**/Shaders/*.glsl` runs
  `vendor/premake/bin/premake5.exe --file=scripts/embed.lua` and writes a byte-array `.inl` into
  the obj dir. It is incremental through MSBuild inputs and outputs, adds no new tool dependency,
  and moves to Linux with premake. Use a **byte array, not a raw string literal**: MSVC caps a
  single literal at about 16 KB.
- **Runtime** *(as built in P0)*: Debug and Debug-ASan define `DE_ENGINE_SHADER_DIR`. If the
  `.glsl` exists there, `Renderer3D` uses `Shader::CreateFromFile` and registers it with
  `Internal::WatchUnmanagedShader` (`src/DingoEngine/Asset/UnmanagedShaderWatch.h`). That is a
  file-static watch list the `AssetManager` poll walks, so the init order doesn't matter.
  Otherwise it uses `CreateFromSource(embedded)`.
  - Release and Distribution always embed. They are what CI publishes, so they carry no
    build-machine path and never run a source file the C++ wasn't built against.
  - There is no compile-failure fallback: Debug asserts on a broken shader at startup, the same
    as any other shader. A broken edit made *while running* keeps the old program, through
    `Reload`'s tolerant path.
- Prebuilt-engine consumers (Gloomdelve) need nothing new: the shader is inside `DingoEngine.lib`.
- The generation-based pipeline and render-pass rebuild already covers every material draw
  (`NvrhiCommandList.cpp:103-185`, `Material.cpp:137-142`). No renderer plumbing is needed beyond
  the watch.

## 4. Verification

**Lighting Test** (`--test=light`). This is also the first test that drives `Renderer3D` itself; none
does today. It follows the `MeshColliderTest` pattern: a real `Scene`, driven by hand.

- A floor and a pillar grid (enough geometry to see pools and occlusion-free spill).
- Toggles and sliders: sun on/off + colour/intensity, ambient, **point-light count 0–64** (orbiting,
  coloured, deliberately past the budget), 2 sweeping spots with cone sliders, `MaxLights` live.
- A row of lit-material spheres, roughness 0 → 1, plus one emissive sphere with a co-located point
  light ("this object *is* the light").
- Pass criteria: no flicker while the scene is static; overflow warns once and shows in F4; spot
  cones have soft inner→outer edges; nothing lights past `Range`.

Also:

- **Backends**: run the test and both migrated examples on Vulkan, DX11 and DX12, using the test
  app's API switch (`test/src/main.cpp:27-35`). The DXBC path is where UBO arrays and loops go wrong.
- **A/B screenshots** before and after P0 and P1: DungeonCrawler3D, EchoVault, Mesh Collider Test.
  Identical is the bar. Per `.claude/reviews/2026-07-29-v0.6.0-review.md`, a passing "before" run
  proves nothing unless it would have failed without the change, so pair each A/B with a
  deliberately broken build.
- **Hot-reload**: introduce a GLSL compile error while running → the old program keeps drawing
  (existing contract, `NvrhiShader.cpp:266-283`).
- **Perf sanity**: F4 frame time at 1080p with 32 lights versus 0, recorded in the review. There is
  no depth pre-pass, so overdraw × lights is the cost to watch.

## 6. *Candlewick* (P8): scope sketch only

A new example under `examples/Candlewick`. It needs the new-executable checklist:
`copyAssimpRuntime()`, a `build-release.yml` packaging step, and `.vscode` build and launch entries.

The vertical slice is 3–5 rooms of a keep:

- A lantern whose radius is a draining resource.
- Wardens carrying moving point lights, with spot-light vision cones. The drawn cone and the
  detection test come from the same data, with line of sight via v0.5 casts.
- Braziers with emissive cores as checkpoints.
- Snuffing the lantern both hides and blinds you.

It stresses the budget honestly: many small static flames and a few moving ones. Write its own plan
once P5 lands, when the real budget and falloff feel are known.

## 7. Risks

| Risk | Mitigation |
|---|---|
| UBO array / loop miscompiles or crawls on the DXBC path | Test DX11/DX12 at P1, not at the end; `[loop]` / keep `LightCounts` dynamic |
| Volatile binding-1 buffers on lit variants not written every frame → NVRHI errors | `Renderer3D` owns the write for every lit material each frame (§2.6) |
| Hot-reload hook runs before the `AssetManager` exists | Hand-off after `AssetManager::Initialize` (`Application.cpp:73`) |
