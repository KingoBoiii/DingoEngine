## Medium

### B1 — Lights whose range contains the camera all tie {#b1}
**Medium · S · CONFIRMED** · `src/DingoEngine/Graphics/Renderer3D.cpp:465-468` (score), `:480-486` (`partial_sort`)

The score is `Brightness / (1 + gap²)` with `gap = max(distance − range, 0)`, so every light whose sphere
contains the camera scores exactly its brightness. Equal-brightness lights then fall to the tie-break,
submission order. With more than 32 such lights the kept set is the first 32 submitted, and a light 1 m
from the camera can be dropped while an identical one 9.9 m away is kept. Torches of range 10 every 2 m
put about 78 lights in range — the *Candlewick* "many small flames" case. The overflow warning ("the
dimmest are dropped") and K16 ("keeps the brightest as seen from the camera") both describe this wrongly.

**Fix:** keep the score and break ties on `distance / range` (closer first) before the index, or make the
in-range score continuous (e.g. `B · (2 − d/r)`). Either stays deterministic.

### B2 — A light without a `Transform3DComponent` blacks out the scene {#b2}
**Medium · S · CONFIRMED** · `src/DingoEngine/Scene/Systems/LightSystem.cpp:38-51`, `:64-69`; `Scene.cpp:46`

`scene.CreateEntity("Lamp").AddComponent<PointLightComponent>()` is the natural first attempt, but
`CreateEntity` adds only the 2D `TransformComponent`. LightSystem counts the component, skips the light
for want of a 3D transform, turns the default sun off, and sets a black ambient: every non-emissive mesh
goes black, with nothing logged. The plan's P7 list mentions invalid lights switching the default off;
this path is far more likely.

**Fix:** warn once per scene when a point or spot component has no `Transform3DComponent`, and don't let
such a light count towards switching the default off.

### O1 — A material drawn by two `Renderer3D`s rebuilds its pipeline twice a frame {#o1}
**Medium · M · code path CONFIRMED, cost PLAUSIBLE** · `src/DingoEngine/Graphics/Material.cpp:125-133`, `Renderer3D.cpp:290`

Every draw calls `SetSceneUniformBuffer` with the drawing renderer's scene UBO, and a pointer change drops
the whole pipeline cache. A material drawn by renderer A then B (made a documented feature by the P4
review's fix 3) therefore compiles a PSO and creates a binding set twice per frame, every frame. The
same pointer comparison has a K18-style hole: a new renderer whose scene UBO lands at a dead renderer's
address leaves the material bound to a buffer nobody writes (PLAUSIBLE).

**Fix:** make the scene UBO part of the cache key — pass it to `GetOrCreateRenderPass` instead of a sticky
setter — keyed by a buffer id rather than the pointer.

### T1 — The Lighting Test has no PASS/FAIL checks {#t1}
**Medium · M · CONFIRMED** · `test/src/Tests/Renderer/LightingTest.cpp` (compare `Renderer3DBatchTest.cpp:19-53`, `MeshColliderTest.cpp:71-78`)

Every v0.7 rule is checked by eye only. Following the batch test's pattern (a private `Renderer3D`, a
fixed view-projection, `GetStatistics()` after each `EndScene`), cheap deterministic checks would be:
nothing submitted → 1 directional; `SetAmbientLight({0,0,0}, 0)` only → 0; an invalid point light → 0
local, 0 directional; 5 directional → 4 kept, 1 dropped; `MaxLocalLights = 100` → budget 32; budget 4 with
6 in view and 2 behind → 4 / 2 culled / 2 dropped; a light submitted before `BeginScene` counts and the
next empty scene is back to the default; and through a throwaway `Scene` — no component → 1 directional,
a disabled point light → 0/0, a point light without a transform → 0/0, two directional components → 2,
`DuplicateEntity` of a light → 2 local. Stage them over several frames: each scene writes the volatile
scene UBO, and Vulkan allows 8 writes per frame ([B7](#b7)).

### T2 — Paths no test or example reaches {#t2}
**Medium · S · CONFIRMED**

- `BeginScene(const glm::mat4&)` and its camera reconstruction (`Renderer3D.cpp:34-42`): the path every
  SceneManager game takes, which feeds specular and light ranking. The Lighting Test calls only
  `BeginScene(PerspectiveCamera)`, even in its entities mode, and no SceneRenderer scene in the tree has
  `Specular > 0` or exceeds the budget.
- The orthographic branch (camera at infinity) in both the shader and the ranking.
- A spot aimed through its entity's `Rotation` (`LightSystem.cpp:55`): the test's spot entities are unrotated.
- `Enabled = false`, several directional components adding their `Ambient`, and `DuplicateEntity` on a light.

**Fix:** have the entities mode call `BeginScene(m_Camera.GetViewProjectionMatrix())` as `SceneRenderer`
does, so the existing direct-vs-entities comparison covers it; give one spot entity a non-identity
rotation with a compensating local direction; and the checks in [T1](#t1).

## Low

### B3 — A texture past slot 0 on a lit material is undefined behaviour on Vulkan {#b3}
**Low (more severe than plan §9 #2) · S · code CONFIRMED, driver effect PLAUSIBLE** · `Renderer3D.cpp:254-263`

NVRHI's Vulkan `createBindingSet` writes a descriptor for every item without checking the layout, so
bindings 4 and 5 reach `vkUpdateDescriptorSets` with a `dstBinding` the layout lacks
(VUID-VkWriteDescriptorSet-dstBinding-00315). Without validation layers that is undefined behaviour; the
fix from the P4 review warns once and keeps drawing. **Fix:** skip the material's draws while
`BindsPastSlotZero` holds.

### B4 — A malformed `#type` line kills a Debug app during hot-reload {#b4}
**Low · S · CONFIRMED** · `NvrhiShader.cpp:549`, `:556`, `:563`, reached from `AssetManager.cpp:631`

`Reload` → `Build` → `PreProcess` asserts on an unknown `#type` (a typo, or a save that ends at `#type
fragment`), and the assert breaks into a debugger that isn't attached. That contradicts the documented
"a broken edit keeps the old program". It predates v0.7 for every file shader, but v0.7 puts the engine's
own shader under it in every Debug app with hot-reload on. **Fix:** log an error and return no sources;
`Build` already treats that as a soft failure.

### B5 — ECS lights are submitted newest-first {#b5}
**Low · S · CONFIRMED (2 reviewers)** · `LightSystem.cpp:26-62`

EnTT views iterate from the back of the packed array, so LightSystem submits the most recently created
entity first. With five directional components the four newest are kept and the oldest — usually the sun
made at setup — is dropped with its ambient. Ties at the local budget go to the newest light, so a
transient light (a muzzle flash) evicts a static one while it lives, and destroying a light reshuffles
ties. A still scene never flickers, but the docs' "first four" and "earlier-submitted" read as creation
order. **Fix:** iterate in creation order (or sort by entity id), or document "newest first".

### B6 — One NaN ambient wipes all ambient, and directional ambient is gated on the wrong count {#b6}
**Low · S · CONFIRMED (2 reviewers)** · `LightSystem.cpp:19-25`, `:69`; `Renderer3D.cpp:337`, `:421`

LightSystem adds the legacy `Ambient` of the first four directional components it *submits*, but
`Renderer3D` keeps the first four it *accepts* (finite ones), so one rejected light shifts which ambients
count. And one non-finite `Ambient` or `AmbientLightComponent` intensity makes the summed ambient NaN,
which `SetAmbientLight` rejects after marking the scene lit: every ambient source is lost, silently.
**Fix:** skip non-finite terms per component, and count ambient only for lights the renderer accepted.

### B7 — Eight writes per frame now bounds the number of 3D scenes {#b7}
**Low · S · CONFIRMED (2 reviewers)** · `Renderer3D.cpp:155`, `:239`, `:326`

Each `EndScene` writes the scene UBO once and `SetUniform`s every lit material it draws, which master's
`DrawIndexed` then re-uploads. All of them use the default `MaxWritesPerFrame = 8`, so on Vulkan a ninth
scene in one frame (six cube-map faces, the main view and a minimap already make eight) has its writes
dropped and draws with the previous scene's camera, lights or material data. `docs/lighting.md` promises
that "a second scene in the same frame starts with no lights" without the limit. **Fix:** create the scene
UBO with a larger `MaxWritesPerFrame` (1808 bytes × versions is cheap), skip `SetUniform` when the lit
data hasn't changed this frame, and document the limit.

### B8 — Pending lights have no frame boundary {#b8}
**Low · S · PLAUSIBLE** · `Renderer3D.cpp:195-245`, `:334-423`

Code that submits lights every frame but runs `BeginScene`/`EndScene` only on some frames (or calls
`EndScene` without `BeginScene`, which returns early) keeps the lights pending, and the next real scene
gets N copies of each: duplicates fill the budget, the sun is counted up to four times, and the log blames
"more than 4 directional lights". A nested `BeginScene` silently drops the meshes already batched.
**Fix:** stamp pending lights with the renderer's frame index and drop (with a warning) any from an
earlier frame; warn when `BeginScene` is called while a scene is active.

### B9 — Debug executables run the checkout's current shader file {#b9}
**Low · S · path CONFIRMED, consequences PLAUSIBLE** · `Renderer3D.cpp:20-24`, `premake5.lua:227`

Documented as a gotcha, but it reaches further: a game linking a locally built Debug `DingoEngine.lib`
runs whatever `Renderer3D_Lit.glsl` the engine checkout has now, so switching that checkout to a branch
that changes `CameraData` breaks lighting in a game that wasn't rebuilt, silently. A broken file in the
tree (mid-edit, conflict markers) also asserts at startup although a valid embedded copy is in the
binary. **Fix:** at startup, warn when the file differs from the embedded copy, and fall back to the
embedded copy if the file fails to compile.

### B10 — The camera position loses precision far from the origin {#b10}
**Low · S · PLAUSIBLE** · `SceneRenderer.cpp:51` → `Renderer3D.cpp:34-42`, `:192`

`SceneRenderer` passes only the view-projection, so the camera position is rebuilt from `inverse(VP)` in
float. For a perspective VP the z and w rows differ only by about `-n·f/(f-n)`, so the error grows with
distance from the origin (the renderer reviewer measured 1e-4 at 2 km, 2e-3 at 10 km). It feeds the
specular view vector and the light scores. **Fix:** a `BeginScene(viewProjection, cameraPosition)`
overload, which `SceneRenderer` calls with the camera entity's position.

### B11 — The watch list and the lit-shader list trust callers to unregister {#b11}
**Low · S · CONFIRMED (needs misuse)** · `UnmanagedShaderWatch.h:11-16`, `AssetManager.cpp:624-632`, `Renderer3D.cpp:97`

Every engine path unregisters before freeing, but a game can free the shader it reaches through
`GetDefaultMaterial()->GetShader()`; the next poll then dereferences it, and a later shader at the same
address would be treated as lit. **Fix:** unregister from both lists in the shader's destructor.

### B12 — Removing the last light brings the default sun back {#b12}
**Low · S · CONFIRMED** · `LightSystem.cpp:64-65`

A scene lit only by point lights that destroys its last light entity, or removes the component rather
than clearing `Enabled`, snaps from dark to the full default lighting in one frame. The docs say a scene
whose lights are all switched off goes dark, which holds only for `Enabled = false`. **Fix:** document
that a deliberately dark scene keeps a permanent `AmbientLightComponent` (black is fine).

### B13 — A Lighting Test frame depends on how the test was entered {#b13}
**Low · S · CONFIRMED (pre-existing harness hazard)** · `test/src/TestLayer.cpp:212-227`, `:268-277`; `LightingTest.cpp:58`

Picked from the list, a test is initialised with an aspect of 1.0 and `Resize` is never called (the
framebuffer already matches), so the image is stretched and `CulledLights` differs from a `--test=light`
boot. The materials mode's crate also arrives through `LoadAsync`, so the first frames differ, and the
header's "frames are repeatable" overclaims. **Fix:** have `TestLayer` call `Resize` right after
`Initialize`, and show when the crate is still loading.

### O2 — Texture changes throw away the pipelines too {#o2}
**Low · S · CONFIRMED** · `Material.cpp:65-83`, `:211-220`

A texture or sampler change only affects the binding set, but `InvalidatePipelineCache` also deletes the
pipelines, so each change costs a PSO compile per cached entry (three for the swap chain alone):
flipbooks and skin swaps will hitch. **Fix:** drop only the render passes, or re-set the slot on them.

### D1 — `SetDirectionalLight` now only sets the fallback {#d1}
**Low · S · CONFIRMED** · `Renderer3D.h:113-114`

Pre-v0.7 code that calls it every frame next to new `SubmitLight` calls loses its sun silently, and the
name invites that. **Fix:** a `SetDefaultLight` with `SetDirectionalLight` deprecated, or a warn-once when
a scene has submitted lights and the fallback was changed.

### D2 — Docs and comments that are wrong or overclaim {#d2}

- `ROADMAP.md:146` calls the Lighting Test "the first test to drive `Renderer3D` itself"; the batch test was.
- `premake5.lua:223-225` and `docs/lighting.md` say Release and Distribution are what gets published, but

- `KNOWN-BUGS.md`: the `{#kNN}` heading anchors don't render on GitHub (PLAUSIBLE, pre-existing); K16's

## Unverified build portability {#portability}

- **Linux (PLAUSIBLE):** under gmake, `Renderer3D.o` has no declared dependency on the generated `.inl`
  until its `.d` file exists, so a clean `make -j` could compile it first. The Linux CI job is disabled
  (`build-master.yml:122`). Make the `.inl` an explicit prerequisite and run the job once.
- **A non-ASCII checkout path (PLAUSIBLE):** the embed step through MSBuild's `.cmd`, premake's argv and
  Lua's `io.open` is untested; a failure would be a loud build error. A `;` in the path would split the
  define.
- **Line endings:** the embedded bytes follow the checkout's line endings (`* text=auto`), so CRLF and LF
  checkouts of one commit produce different libraries and shader-cache hashes. `*.glsl text eol=lf` fixes it.

## Nits {#nits}

- Per-pixel work that could move to the CPU: the directional `normalize` (normalise once on the CPU, which
  also rejects zero directions), `toCamera` normalised even without specular, and the full 1808-byte UBO
  uploaded whatever the light count.
- `Statistics::DroppedLights` doesn't count lights past the 8192 pending cap.
- `LightSystem` replaces an ambient a game set directly with `SetAmbientLight` before the scene renders.
- A save during the lit shader's first compile is missed until the next save (the timestamp is taken
  after the compile).
- Command-line flags: `--specular=OFF`/`0`/`false` leave specular on, `--entities=false` and `--night=0`
  turn the feature on, the test starts in the "lights" mode (undocumented), and `--entities` is ignored
  with `--lighting=materials`.
- `Renderer3D.cpp:151-154` repeats the header comment; `LightingTest.cpp:340` narrates.

## Checked and found correct

- **std140:** `CameraData` offsets (0, 64, 80, 96, 112, 128, 144, 272), strides 32 and 48, 1808 bytes
  total, all `static_assert`ed; `LitMaterialData` matches the shader. The vertex stage declaring only the
  first 64 bytes of binding 0 is valid on every backend.
- **HLSL/DXBC:** dynamic loops over constant-buffer struct arrays, `int4` counts, the texture sample
  outside flow control, `pow` with a non-negative base, a guarded `inversesqrt`.
- **NVRHI binding de-duplication** keyed by type and slot, taking the largest array size.
- **NaN safety:** the shader's light loop and every CPU light and material input.
- **Culling:** Gribb–Hartmann planes for [0,1] depth, near and far included, orthographic too.
- **Selection:** a strict weak ordering, deterministic on a still scene; spot cone scale/offset and clamps.
- **The default light** reproduces the pre-v0.7 `a + (1 − a)·N·L` exactly, on both paths.
- **Lifetimes:** idle batch release never frees a batch in the draw order; invalidating a material's cache
  mid-frame is safe because NVRHI keeps recorded pipelines and binding sets alive; shutdown unregisters
  before freeing; the examples free their lit materials before the renderer shuts down.
- **Volatile writes:** no buffer is ever bound unwritten.
- **Components:** registered in `DE_INSTANTIATE_COMPONENT` and `DuplicateEntity`, no runtime handles; a
  spot's aim is `Rotation · Direction` with the engine's −Z forward.
- **Build:** the embed step runs before compilation with per-configuration outputs; editing the `.glsl`
  or `embed.lua` rebuilds what depends on it; paths are quoted; a clean CI checkout works;
  `DE_ENGINE_SHADER_DIR` exists only in Debug and Debug-ASan.
- **Hot-reload plumbing:** the watch list is constant-initialised, main-thread only and order-independent;
  a failed recompile keeps the old program.
- **Docs:** every snippet compiles, every anchor resolves, every formula and default matches the code.
- **Tests and examples:** no uninitialised state in the Lighting Test; DungeonCrawler3D's `--seed` parsing
  rejects bad input; EchoVault's lights and materials have correct lifetimes and stay well under budget.
