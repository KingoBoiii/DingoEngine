## High

### V1 — Sprites draw upside down and flipbook rows play bottom to top {#v1}

`ParticleDraw.glsl:63-66`. CONFIRMED.

**What happened:**
- The vertex stage mapped the quad's top (`corner.y = +1`, along `CameraUp`) to v = 0, which is texel row 0. Every file texture loads flipped (`ReadImage(..., flipVertically = true)`), so row 0 is the bottom of the image. Renderer2D maps its top vertices to v = 1, which is why its sprites stand upright.
- `cell.y = floor(frame / columns)` counted flipbook rows from v = 0, so a flipbook started on the image's bottom row, against the documented "left to right, top to bottom".
- Random start rotation ([V2](#v2)) hid the flip on round sprites, but not the frame order. P14's flame flipbooks need both.

**Fix:** count rows from the top (`row = rows − 1 − floor(frame / columns)`) and map the quad's top to v = 1. The Particle Test reads back a 2x2 flipbook's first and third frames at the particle's centre.

### P1 — A file `#include`d by two stages reaches only the first {#p1}

`ShaderIncludes.cpp:112-113, 134-135`, called from `NvrhiShader.cpp:590, 609`. CONFIRMED.

**What happened:**
- `GetShaderSources` expanded the whole multi-stage file, with one set of pasted files, and only then `PreProcess` split it on `#type`. So a `Common.glsl` included by the vertex and the fragment stage, the usual pattern, was pasted into the vertex stage only.
- The fragment stage then failed to compile, and the next pipeline build hit `DE_CORE_ASSERT(vsHandle && ...)` in Debug. The same happened to an include under `#ifdef A` and again under `#else`.
- No engine shader includes one file from two stages, so nothing in the tree showed it. The Render Target Test included one file twice in a single stage, and its `partCount == 1` treated the cross-stage behaviour as correct.

**Fix:** `PreProcess` first, then expand each stage on its own (`NvrhiShader::ExpandStages`). Each file is listed once for the hot-reload watch. This also lifts the rule that an included file must never contain `#type`. The Render Target Test includes `include-common.glsl` from both stages.

### S1 — Local shadow slots go in submission order while the lights fit the budget {#s1}

`Renderer3D.cpp:1029-1078` with `:1435-1535`. CONFIRMED.

**What happened:**
- `ResolveSceneLights` sorts `m_VisibleLocalLights` only when the visible lights overflow `MaxLocalLights`. Otherwise the list stays in submission order.
- `PrepareLocalShadows` gave the shadow slots, the tile tiers and the fade cutoff to `casting[0..cap)` in that order.
- **Example:** 20 casting torches, a 32-light budget and 8 slots. The first 8 created get shadows, the first two get the 1024² tiles, and the torches by the camera light unshadowed.
- With `LightBudgetFade > 0` it is worse. `shadowCutoff` was the 9th *submitted* light's priority, so a slot-holding light ranked below it faded to no shadow while a better-ranked light had none.
- The Shadow Test's budget check compared counts only, so it passed.

**Fix:** rank the casting lights with the budget's own comparators before giving out slots: `Priority` with a fade band, else `Score`, then `Nearness`, then index. `m_VisibleLocalLights` keeps its order, because the lit shader sums the lights in it and reordering would break the 0 px rule (D2).

## Medium

### V2 — Every particle starts at a random rotation, with no way to turn it off {#v2}

`ParticleSimulate.glsl:192`. CONFIRMED.

`Misc.y = ParticleRandom(state) * TAU` runs for every particle, and `Spin` only sets the rate. So flames, streaks, arrows and other sprites that have an up can never stay upright, even with `Spin(0, 0)`, and the docs don't say so.

**Fix:** add `ParticleEffectParams::StartRotation`, a degrees range, in a spare record lane, and emit it in `ParticleEffectToCode`. It should default to 0..0, or to 0..360 if random stays the default.

### V3 — A scene drawn by two `Renderer3D`s rebuilds its emitters every pass {#v3}

`ParticleSync.cpp:151-157`. CONFIRMED.

`runtime.Owner != &renderer` recreates the emitter whenever another renderer submits it.
- **Two renderers:** a game calls the public `RenderEntities3D` with its own `Renderer3D` (a minimap) as well as the `SceneRenderer`. The owner flips every pass, so every pass releases the ring, clears a new one and loses every live particle. No particle outlives a frame.
- **Address reuse:** a renderer freed and replaced at the same address keeps the old emitter. `ParticleRenderer::Submit` rejects it as foreign (warned once), and that entity never draws particles again.

**Fix:** key by renderer identity, not address (a per-renderer id, or a `weak_ptr` to the pool), and keep one emitter per renderer, or submit only to the owner.

### V4 — The draw material's UBO has 8 Vulkan writes a frame against 32 scenes {#v4}

`ParticleRenderer.cpp:405-409`. CONFIRMED.

Each (sprite, blend, depth) draw material's UBO is a default `CreateUniformBuffer` with `MaxWritesPerFrame` 8, and `EndScene` calls `SetUniform` once a scene. Renderer3D allows `k_MaxScenesPerFrame` (32) scenes a frame. From the 9th scene drawing the same particle batch in one frame (split screen, minimaps, several `SceneRenderer::Render(scene, target)`), Vulkan drops the write. The draw then uses an earlier scene's camera and `Batch` offsets against this scene's emitter records, so particles land in the wrong place with the wrong emitters' settings.

**Fix:** size the UBO for `k_MaxScenesPerFrame` (a `MaterialParams` knob, or a volatile UBO the particle renderer owns), or move the per-scene camera and batch data into the emitter storage buffer.

### V5 — A duplicated `ParticleEventComponent` drives the original's emitters {#v5}

`Scene.cpp:124`, `ParticleSync.cpp:83-90`. CONFIRMED; documented in docs/particles.md, but a trap.

`DuplicateSubtree` copies the bindings with the original emitters' UUIDs.
- Fighters spawned by duplicating a template puff every clone's dust at the template's feet, and the clones' own emitters never fire.
- Destroying a clone runs `StopRanges` on the original's range emitters, cutting its trail mid-swing.
- The docs' advice to "bind its own afterwards" leaves the old bindings in place, because `Bind` appends.

**Fix:** in `DuplicateSubtree`, map old to new UUIDs for the copied subtree and rewrite each copied binding that points inside it.

### P2 — `Begin`/`End` ignore and drop the caller's viewport {#p2}

`PostProcess.cpp:487-513, 584, 617`, `FullscreenPass.cpp:36-42`. CONFIRMED.

`Begin` keeps the caller's render target but not its viewport. The scene target is sized to the whole caller, and `End` tone-maps into the whole caller and never restores the viewport. In split screen (`SetViewport(left half)`, Begin → 3D → End, then the right half), each `End` overwrites the whole swap chain, so only the last view survives, stretched. Later draws also run without the viewport. `SetViewport` is new in v0.9, so this is not a regression.

**Fix:** a `Renderer` viewport query; size the scene target to the viewport, tone-map into it, and restore it after.

### P3 — Same-size scenes in one frame share one scene target and fight over it {#p3}

`PostProcess.cpp:382-389` (the size match ignores `LastFrame`), `:194-199, 599-603, 616`. CONFIRMED.

Every `Begin` of one output size in a frame shares one `SceneTarget`: its tone-map material, bloom chain and AO chain. Two scenes with different settings, for example `Render(sceneA, targetA)` and `Render(sceneB, targetB)` into two 640x360 targets, fight over it every frame:
- **Bloom on in one and off in the other:** slot 1 is switched twice a frame. Each switch invalidates the pipeline cache, so the pipeline is rebuilt twice a frame.
- **AO `HalfResolution` differs:** the AO targets are resized (new GPU textures) twice a frame.
- **Vulkan write budget:** each settings change is a write to the one tone-map UBO. More than 8 differing same-size `Begin`s a frame read stale settings. The Post Test's first frame already makes 7 such writes on its 256x1 target.

**Fix:** match only a target with `LastFrame != frame`, so each `Begin` of a frame gets its own.

### P4 — The pipeline cache keys a framebuffer by address, and v0.9 frees framebuffers at runtime {#p4}

`Material.cpp:22`, `PostProcess.cpp:373-377`. PLAUSIBLE: it needs a reuse at runtime.

Material pipeline caches hash the `Framebuffer*` address with no generation. The post chain now frees framebuffers at runtime (an idle scene target after 300 frames, with its bloom, AO and depth-copy targets) and brings new formats.

**Scenario:** an RGBA8 + depth target allocated where an RGBA16F scene target was gets the shared default or lit material's old pipeline. That is a format mismatch: an NVRHI validation error, undefined behaviour or device removal on D3D12, and an incompatible render pass on Vulkan. This existed before v0.9, but back then nearly every framebuffer was RGBA8.

**Fix:** a never-reused `Framebuffer::GetId()`, keyed like `Mesh`/`Material` ids, or a global framebuffer generation that invalidates the caches, as swap-chain resizes already do.

### S2 — Shadow probes stall the CPU on the GPU every frame they run {#s2}

`Renderer3D.cpp:1715-1723` → `NvrhiTexture.cpp:187-228`. CONFIRMED.

`DrawShadowProbes` calls `ReadPixels`, which makes a new staging texture and resolves it in the next `BeginFrame`. `mapStagingTexture` waits there for the frame just submitted, on every backend. `Scene::GetLightVisibility` is meant to be called every frame, so a game using it loses all CPU/GPU overlap (frame time becomes CPU + GPU). It also allocates a staging texture per probing scene per frame. That contradicts the header's "never stalling".

**Fix:** a ring of 3–4 persistent staging textures, each with an event query, mapped only once the query reports it done. Answers then arrive 2–3 frames late, as the plan designed.

### S3 — A casting scene drops the caller's viewport {#s3}

`Renderer3D.cpp:1550-1551, 1609`, `FullscreenPass.cpp:38-41`. CONFIRMED.

`DrawShadowPass` and `DrawShadowProbes` switch the render target to the atlas or the probe target and back, and `SetRenderTarget` clears the viewport. Both run inside `EndScene` before the lit draws, so a viewported shadowed scene draws its lit pass over the whole target. This is the same root cause as [P2](#p2), and not a regression.

**Fix:** an internal save and restore of target plus viewport, used by the shadow pass and both `DrawFullscreen` overloads.

### C1 — No barrier between two operations with the same bindings; `ReadBack` leaves the buffer's state changed {#c1}

`NvrhiCommandList.cpp:264-278`, `NvrhiGraphicsBuffer.cpp:153-158`. CONFIRMED against NVRHI's state tracking (`ProgrammingGuide.md:50`).

NVRHI re-applies a binding set's resource states only when the bound sets change.
- **Same pass twice:** `Renderer::Dispatch(pass)` twice in a row with the same `ComputePass`, as an iterative kernel would, gets no UAV barrier. On Vulkan and D3D12 the second dispatch races the first.
- **Copy in between:** an `Upload` or `ReadBack` between two operations with the same state leaves the buffer in a copy state with no barrier back.
- `ReadPixels` already restores the state; `ReadBack` doesn't. The particle path happens to avoid both, because a graphics draw or another binding set always sits in between.

**Fix:** set every storage binding's state (`UnorderedAccess` or `ShaderResource`) before each dispatch and draw, which gives a UAV barrier when needed. In `ReadBack`, restore the previous state as `ReadPixels` does.

### C2 — `GraphicsBuffer::Upload` and initial data never reach a storage buffer {#c2}

`NvrhiGraphicsBuffer.cpp:81-105`, `GraphicsBuffer.cpp:49-56, 63-66`. CONFIRMED.

`CreateStorageBuffer` makes the buffer with `DirectUpload(false)`, so `Upload` only keeps the caller's pointer and records nothing. A storage buffer filled once at start-up is uninitialised on Vulkan and D3D12, and the one-argument `Renderer::Upload(buffer)` later reads that pointer, which may be dangling by then. Only `Renderer::Upload(buffer, data, size)` inside a frame works, against `GraphicsBuffer.h:119` and docs/compute.md.

**Fix:** for storage buffers, copy the bytes and use `ReadBack`'s timing (the frame list, a one-off list while parked, else `RunAfterFrame`), and add `initialData` to `CreateStorageBuffer`. Failing that, correct both docs.

## Low

### V6 — A range that opens and closes in one frame never plays {#v6}
`ParticleSync.cpp:125-128`, CONFIRMED. `RangeBegin` then `RangeEnd` in one update (a short range, a low frame rate or a seek) sets `Playing` true and back to false before `Submit`, so not even `BurstOnPlay` fires. **Fix:** on `RangeBegin`, also queue the effect's `BurstOnPlay`.

### V7 — Bursts queue without bound on an emitter that can't draw {#v7}
`Particles.cpp:113-123`, `ParticleRenderer.cpp:185-186`, `ParticleSync.cpp:144-149, 191`, CONFIRMED. `Emit` on an emitter with capacity 0 queues forever, and so does `runtime.Bursts` on an entity without a `Transform3DComponent` or with a null `Effect`. **Fix:** make `Emit` a no-op at capacity 0, and clear the runtime bursts when the entity can't submit.

### V8 — An ECS emitter that found the pool full is never retried {#v8}
`ParticleSync.cpp:152`, CONFIRMED. A runtime emitter with capacity 0 is non-null, so it is never recreated: an entity spawned while the pool was full stays dark for life. **Fix:** recreate at capacity 0, throttled to about once a second.

### V9 — A submission keeps a raw `ParticleEmitter*` until `EndScene` {#v9}
`ParticleRenderer.cpp:187`, PLAUSIBLE. Through the direct API, dropping the last `shared_ptr` between `SubmitParticles` and `EndScene` leaves `EndScene` reading freed memory; the ECS can't do this. **Fix:** hold a `shared_ptr`, or document the lifetime.

### V10 — The live-effect registry can die before the last effect {#v10}
`Particles.cpp:12-16, 107-110`, PLAUSIBLE. The registry is a function-local static. An effect owned by a global declared before the first effect was made is destroyed after it, at exit. **Fix:** leak the registry.

### V11 — A ring stays uncleared after a dispatch that didn't run {#v11}
`ParticleRenderer.cpp:353`, PLAUSIBLE. `m_NeedsClear` is reset even when the dispatch didn't run (a compute shader broken by a Debug hot-reload), so the ring later draws stale slots. **Fix:** have `Dispatch` report success.

### V12 — Duplicate effect names collide as ImGui ids; the generated code has gaps {#v12}
CONFIRMED.
- `ImGuiDebugPanels.cpp:54-65`: effects with the same `DebugName` share an ImGui id. **Fix:** `PushID(effect)`.
- `ParticleEffectToCode` (`Particles.cpp:38-90`):
  - it drops a 1x1-flipbook sprite;
  - it emits an undeclared `texture`;
  - it pastes `DebugName` unescaped;
  - it prints non-finite floats as `inff` or `nanf`.

### V13 — The pool's creation and the simulate/emit order are misdescribed {#v13}
CONFIRMED.
- `Renderer3D.h:225-226` says "emit, then simulate"; the code simulates, then emits.
- `Renderer3D.h:79` and docs/particles.md:110 say the pool is made with the first emitter; it is made at the first `EndScene` with a submission.

### V14 — The Particle Test proves less than it says {#v14}
CONFIRMED.
- No check drew a sprite or a flipbook. Fixed with [V1](#v1).
- Nothing covers random rotation.
- The motes check never asserts that the motes are off before `look` opens.
- "None outlive their lifetime" leans on a step longer than the short emitter's life.

### P5 — With post on, the caller's depth is never written {#p5}
`SceneRenderer.cpp:67-77`, `PostProcess.cpp:513`, CONFIRMED. The 3D pass clears and writes the scene target's depth only. A later 3D draw into the caller (a custom pass, a gizmo) tests against a stale depth from earlier frames. **Fix:** copy the scene depth back in `End`, or at least clear the caller's depth, and document which.

### P6 — A +Inf pixel turns bloom into NaN across all six levels {#p6}
`PostBloom.glsl:39-84`, `ToneMapping.glsl:12-22`. The maths is CONFIRMED; whether it happens in practice is PLAUSIBLE. RGBA16F stores values past 65504 as +Inf. The prefilter's threshold and Karis weight then give NaN, which the filters spread into a black or white block. **Fix:** clamp the prefilter's taps and the tone map's input to about 65000, and drop non-finite values.

### P7 — The half-resolution AO upsample bleeds across silhouettes {#p7}
`PostAmbientOcclusion.glsl:139-148`. The test gap is CONFIRMED; how visible the bleed is is PLAUSIBLE. The apply pass upsamples bilinearly with no depth test, so contact darkness bleeds about a pixel onto an object's edge. The Post Test's no-halo check looks where AO is 1 on both sides, so it can't fail. **Fix:** a depth-aware 2x2 upsample, and a check at the resting box's base.

### P8 — A quoted include at an engine shader's top level fails in Release {#p8}
`ShaderIncludes.cpp:105-131`, `EngineShaders.cpp:81-87`, CONFIRMED but latent. In Debug the file resolves next to the shader; in Release the embedded source has no path and resolves against the asset root. Every engine shader uses angle brackets today. **Fix:** mark the top-level origin as Engine in `CreateEngineShader`.

### P9 — A missing include isn't watched, so it never triggers a reload {#p9}
`ShaderIncludes.cpp:143-150`, CONFIRMED. The watch is added after the existence check, against the comment there. A shader naming a file that doesn't exist yet doesn't reload when the file appears. **Fix:** watch the path before the check (a missing file already reads as the epoch).

### S4 — Probes answer for the first render of the frame, whichever camera it had {#s4}
`LightSystem.cpp:142, 228-229`, CONFIRMED code path. `Pending` is issued and cleared at the scene's first `SubmitLights` of a frame. A minimap `Render` before the main one answers from the minimap's cascades and culling. **Fix:** prefer the primary camera's render, or document the rule.

### S5 — Caster bounds cost O(vertices) per submission even when nothing casts {#s5}
`Renderer3D.cpp:556-574, 1188-1202`, CONFIRMED. `ShadowCasting::On` is the default, so every scene now pays for caster bounds: `SubmitSkinnedMesh` transforms every rest vertex, and `SubmitMesh` walks every vertex a second time. **Fix:** a model-space AABB on `Mesh` (8 corners), with the min/max folded into the existing transform loop.

### S6 — A skinned mesh skipped by the lit pass still casts {#s6}
`Renderer3D.cpp:770-771` against `:1593-1603`, CONFIRMED. A lit material with a slot past 0 skips the lit draw but not the skinned shadow draw, which leaves a shadow with no character. **Fix:** apply the same skip in the shadow loop.

### S7 — A probe outside the camera's cascades reads lit {#s7}
`Shadows.glsl:54-105`, CONFIRMED. A point behind the camera or off screen maps outside every tile, so AI asking about off-screen points gets "lit". **Fix:** document it, or fall back to the last cascade.

### S8 — Shadows use `ClipDistance` without checking that Vulkan has it {#s8}
`VulkanGraphicsContext.cpp:546`, `Renderer3D_Shadow.glsl:31-35`, PLAUSIBLE. A device without `shaderClipDistance` gets an invalid shadow pipeline with no warning. **Fix:** warn once and turn shadows off.

### S9 — A sun with `ShadowStrength` 0 still renders every cascade {#s9}
`Renderer3D.cpp:875-881`, CONFIRMED. Local lights skip a strength of 0; the sun doesn't. **Fix:** skip it the same way.

### S10 — Two scenes on one renderer share the tier hysteresis {#s10}
`Renderer3D.cpp:1427-1428`, CONFIRMED. `m_LocalShadowTiers` is per renderer and keyed by submission index. A main view and a minimap with the same light count overwrite each other's tiers every frame. **Fix:** key the tiers by the light's position and range, or keep one table per camera.

### C3 — A storage binding's SRV/UAV choice is frozen when it is set {#c3}
`NvrhiComputePass.cpp:156-182`, `NvrhiRenderPass.cpp:101-123`, CONFIRMED. A hot-reload that adds or drops `readonly` rebuilds the layout but keeps the old item type. D3D12 then gets a null descriptor and D3D11 an unbound slot; Vulkan doesn't care. **Fix:** keep the buffer per binding and build the item from the current reflection.

### C4 — Fragment-stage storage writes are advertised but unsupported {#c4}
`RenderPass.h:42-43`, CONFIRMED.
- Vulkan never enables `fragmentStoresAndAtomics`.
- D3D11 binds pixel UAVs from the first slot past the render targets.
- **Fix:** drop the claim from the comment, or enable the feature and document the D3D11 slot rule.
- PLAUSIBLE: storage images in R8, R16F and R11G11B10F need `shaderStorageImageExtendedFormats` on Vulkan.

### C5 — `SetStorageBuffer` compares addresses and rebuilds pipelines {#c5}
`Material.cpp:150-170`, CONFIRMED. A buffer replaced at the same address is missed. Every change destroys the PSOs, so ping-ponging two buffers recompiles every frame. **Fix:** compare `GetId()` and re-bake only the binding sets.

### T1–T5 — Shadow Test checks that pass while broken {#t1}
<a id="t2"></a><a id="t3"></a><a id="t4"></a><a id="t5"></a>
CONFIRMED.
- **T1:** the budget check compared counts only, so [S1](#s1) was invisible to it. Fixed by the rank check in `747b185`.
- **T2:** the fade check reads only `Statistics::FadedLights`, which the code under test computes. Its lights don't cast, so the slot hand-over through the band is untested.
- **T3:** the acne check would pass if the atlas never rendered; it has no positive control.
- **T4:** "a still scene draws the same frame twice" draws both in one frame, so it can't catch frame-to-frame instability.
- **T5:** the probe checks read after 8 frames, so they can't verify "a frame or two" or see [S2](#s2).

### T6 — The Compute Test can't see barriers or `Upload` {#t6}
CONFIRMED. It checks only the first frame. It never runs the [C1](#c1) or [C2](#c2) paths (one pass dispatched twice, an upload between two operations with the same state, `GraphicsBuffer::Upload`). On Vulkan, read-only and writable blocks look alike.
